# Engineering Decision Log

## 1. Extend the existing `Invoice` model rather than build a parallel one

**Decision**: Made `Invoice.orderId` optional and added `InvoiceItem`, `InvoiceDiscount`, `InvoicePayment`, `Promotion` as new related models, instead of creating a second, separate "ManualInvoice" concept.

**Reason**: The spec's sample data (cash payment, stacked discounts, USPS tracking, no Stripe order) is clearly a manual/off-platform sale, but the existing `Invoice` model was hard-wired 1:1 to a Stripe `Order`. Two invoice concepts in one app would confuse "which one do I query" at every future call site.

**Alternatives considered**: A separate `ManualInvoice` model entirely independent of `Invoice`.

**Benefits**: One invoice concept, one dashboard, one PDF pipeline, regardless of sale origin. Satisfies Part 1's "maintain the current project architecture, do not unnecessarily restructure."

**Drawbacks**: The `Invoice` model is now larger and carries fields (`orderId`, `stripeInvoiceId`) that are irrelevant to manual invoices, and fields (`items`, `discounts`) that are irrelevant to the original Stripe-order use case. Judged acceptable — both paths share the same lifecycle (draft → paid, ship → deliver) far more than they differ.

## 2. Persist in Postgres/Prisma now, not localStorage

**Decision**: All invoice data goes straight into the existing Neon/Prisma database via `lib/invoices.ts`.

**Reason**: The spec says "saved locally for now," anticipating a future swap to a real database — but Neon/Prisma is already fully provisioned and used for every other entity in this app. Building a throwaway localStorage layer specifically to replace it later would itself be the "quick hack" Part 1 says never to build.

**Alternatives considered**: Browser localStorage now, migrate later.

**Benefits**: No throwaway code. The actual swap-seam the spec wants (storage can change with minimal code impact) still exists — it's `lib/invoices.ts`, the single module every route/page calls instead of touching Prisma directly.

**Drawbacks**: None identified — the "future storage flexibility" goal is met without the localStorage detour.

## 3. PDF generation via `@react-pdf/renderer`, not an overlay on the two sample PDF files

**Decision**: Build both PDF documents from React component trees (`lib/invoice/pdf/MasterInvoiceDocument.tsx`, `RecipientReceiptDocument.tsx`) rather than positioning text onto the two fixed-position sample PDFs referenced in Part 1's placeholder comments.

**Reason**: Those sample PDFs are example output for one specific invoice (3 items, 2 discounts). Real invoices have unlimited items and stacking discounts — a fixed-position overlay can't reflow to fit variable content. `@react-pdf/renderer` is pure JS (no headless-Chromium binary), which avoids a known pain point deploying Puppeteer-style HTML-to-PDF on Vercel serverless functions.

**Alternatives considered**: Puppeteer/Playwright rendering an HTML page to PDF (would guarantee pixel parity with the live preview, at the cost of a much heavier serverless deployment); pdf-lib overlay onto the static template files.

**Benefits**: Reflows correctly for any number of items/discounts; lightweight; no binary/runtime concerns on Vercel.

**Drawbacks**: The live HTML preview and the generated PDF are visually aligned (same brand constants) but not pixel-identical, since `@react-pdf/renderer` uses its own layout primitives rather than real DOM/Tailwind.

## 4. PDFs generated on-demand, not stored as files

**Decision**: `GET /api/admin/invoices/[id]/pdf` streams the PDF directly on each request. `pdfMasterUrl`/`pdfRecipientUrl` remain nullable columns, unused for now.

**Reason**: No blob storage (Vercel Blob, S3, etc.) is configured in this project yet. Adding one just for this feature would be new infrastructure the spec doesn't explicitly require, and on-demand generation is fast enough for the current scale (a single admin generating PDFs, not a high-throughput customer-facing flow).

**Alternatives considered**: Generate once on save, upload to blob storage, store the URL.

**Benefits**: No new infrastructure dependency; PDF always reflects the current invoice state (no stale cached file after an edit).

**Drawbacks**: Regenerates on every download rather than serving a cached file — acceptable at current volume; revisit if invoice volume or PDF complexity grows enough to matter.

## 5. Sequential invoice numbering is new, separate from the existing random-suffix generator

**Decision**: Added `generateSequentialInvoiceNumber()` in `lib/invoice/numbering.ts` for the new invoice endpoints; left `generateInvoiceNumber()` in `lib/orders.ts` (random suffix, e.g. `INV-202607-A1B2C`) untouched for its existing caller.

**Reason**: Part 2 explicitly requires sequential, non-reused numbers (`PS-2026-000001`). Changing the existing function's behavior would silently alter the Stripe-order invoice path's numbering format with no upstream reason to do so.

**Benefits**: Zero behavior change to existing, working code; new requirement met exactly as specified.

**Drawbacks**: Two invoice-numbering schemes now exist in the codebase (`INV-YYYYMM-XXXXX` vs `PS-YYYY-NNNNNN`). Worth unifying if/when the Stripe-order invoice path is ever merged into this module's data model (see Decision #1's drawback).

## 6. One new runtime dependency: `zod`

**Decision**: Added `zod` for invoice/payment payload validation.

**Reason**: The spec explicitly requires validation of required fields, email/ZIP format, non-negative totals, overpayment guards, and duplicate invoice numbers. No existing dependency in the project provides schema validation.

**Alternatives considered**: Hand-rolled validation functions.

**Benefits**: Declarative, type-inferring schemas (`InvoicePayload`/`PaymentPayload` types are derived from the schema, not maintained separately); well-established, lightweight, no runtime bloat.

**Drawbacks**: One more dependency to keep updated — judged worth it given how much validation surface the spec requires.

## 7. Branch workflow: `feature/invoice-system` off `master`, PR at the end

**Decision**: Branched off `master` (the full e-commerce app), not `landing` (the pre-launch marketing page) — even though the design language is sourced from `landing`. Work is pushed to GitHub incrementally; a PR is opened once the module is complete rather than merging directly.

**Reason**: The invoice system is an internal admin tool that depends on Prisma/Clerk/the admin dashboard, none of which exist on `landing`. `landing` is purely a marketing page's source — useful as a design reference, not a base to build on.

**Benefits**: Design consistency without incorrectly coupling an internal tool's codebase to the marketing page's branch.

## 9. Fixed `eslint.config.mjs` to import `eslint-config-next`'s flat config directly, not through `FlatCompat`

**Decision**: Replaced `compat.extends('next/core-web-vitals', 'next/typescript')` with direct imports of `eslint-config-next/core-web-vitals` and `eslint-config-next/typescript`.

**Reason**: `eslint-config-next@16.2.6` ships native ESLint 9 flat-config arrays (confirmed by reading its compiled `dist/*.js` — they're array spreads of real plugin objects, not legacy eslintrc strings). `FlatCompat.extends()` exists specifically to shim *legacy* eslintrc-style shareable configs into flat config; passing already-flat, self-referencing plugin objects through its legacy JSON-schema validator crashed with "Converting circular structure to JSON" the moment `eslint .` was run directly. This surfaced now (not earlier) because Next.js 16 removed the `next lint` subcommand entirely, so `eslint .` became the only way to lint this project — and that path had never actually been exercised before.

**Alternatives considered**: Disabling lint / adding broad ignores (rejected — hides real errors); downgrading `eslint-config-next` (rejected — no reason to fight the version already required by Next 16).

**Benefits**: `npx eslint .` now runs and reports real findings. Fixing it surfaced four genuine issues in code this PR touched — two `react-hooks/set-state-in-effect` violations (`InvoiceTable.tsx`, `ClerkAuthButtons.tsx`, both fixed), and a false-positive `jsx-a11y/alt-text` warning on `@react-pdf/renderer`'s `Image` (which renders into a PDF content stream, not the DOM — suppressed with a comment explaining why).

**Drawbacks**: None — this is a straightforward compatibility fix, not a workaround.

**Benefits**: Dashboard/builder now visually matches the live site the owner actually showed as the reference. All dark-theme class tokens live in one file (`components/invoices/theme.ts`) instead of being re-typed per component, so a future token change is a one-file edit.

**Drawbacks**: `/admin`'s non-invoice pages (the base dashboard, orders table) still use the old light theme — there's now a visible seam at the `/admin` → `/admin/invoices` boundary. Acceptable for now per the same "that can be handled later" scope boundary as Decision #8; flagged in `FutureRoadmap.md`.

## 11. Legal footer: centralized config + one shared PDF component, normal document flow only

**Decision**: Added `lib/invoice/legal.ts` (`INVOICE_LEGAL_SECTIONS`) as the single source for the RUO and Customer-Responsibility-After-Delivery clauses, and a `LegalFooter` component in `lib/invoice/pdf/shared.tsx` used by both `MasterInvoiceDocument.tsx` and `RecipientReceiptDocument.tsx`. Replaced the old `fixed`-positioned one-line `DocumentFooter` entirely — `LegalFooter` renders in normal document flow, after the totals/payment-history/notes content, never at an absolute page position.

**Reason**: A `fixed` footer is pinned to the same spot on every page regardless of how much content precedes it; that's fine for a one-line tagline but risks visually colliding with totals or overflow content once real legal paragraphs are added. Rendering after the rest of the content in normal flow makes "never overlaps totals" true by construction rather than something to test for. Centralizing the copy in one file (rather than duplicating the same paragraphs in both PDF documents) means a future legal wording change is a one-file edit.

**Alternatives considered**: Keep the `fixed` footer and just lengthen it (rejected — reintroduces the overlap risk this decision exists to avoid); duplicate the legal text directly in each PDF document (rejected — violates the "no duplicated legal text" requirement and risks the two copies drifting).

**Benefits**: Overlap-proof by construction; single edit point for legal copy; `wrap={false}` keeps each clause intact rather than splitting a paragraph across a page break if the footer is ever pushed to a second page.

**Drawbacks**: On an unusually long invoice (many items, long notes), the footer can be pushed entirely onto a second page. Judged acceptable — better than clipping or overlapping — and not expected in practice given typical invoice length.

## 12. PDF header gets a small gold accent bar and status badge; sparing use of gold elsewhere in print

Everything else in the PDF — body text, table rules, section borders — stays black-on-white.

Gold is the brand's one accent color; using it in exactly two deliberate spots (a small header accent, and the one status worth highlighting) reads as intentional brand presence without turning the document into a colored flyer or wasting ink on a black-and-white printer.

**Alternatives considered**: Color-code every status like the on-screen `StatusBadge` does (rejected — would mean 6+ colors in a printed document, working against "less is more" and printer-friendliness); no status badge at all (rejected — a quick-scan paid/unpaid indicator is genuinely useful on a printed record).

**Benefits**: Consistent, restrained brand presence in the PDF; status is scannable at a glance without re-reading the totals block.

**Drawbacks**: None identified.

## 13. Product picker matches on a composed "Name — Size — 1 Box" label, not the bare product name

**Decision**: `InvoiceItemsTable.tsx`'s product datalist now displays and matches against `formatProductLabel(product)` (`lib/invoice/format.ts`) — e.g. `Tesamorelin — 10mg — 1 Box` — instead of `product.name` alone. Selecting a product now also saves that full composed label as the invoice line item's `name`, not just the bare name.

**Reason**: The catalog reuses the same `name` across multiple strengths (Tesamorelin 5mg/10mg, Semaglutide across five strengths, etc.) but the picker matched purely on `product.name`. With two products sharing a name, `products.find(p => p.name === typed)` always resolved to whichever row happened to come first — the dropdown couldn't actually distinguish strengths, and even when the right one was intended, only the bare name (no strength) was saved onto the invoice line item, PDF, and receipt. This was flagged directly: invoices were losing the mg strength, and duplicate-looking dropdown entries made it easy to pick the wrong price.

**Alternatives considered**: Switch the picker to a real `<select>` keyed by product id (rejected — would drop the existing free-text/ad-hoc-item support the datalist provides, a real feature per the original spec's non-catalog sample items like "Glow70"); keep matching on name but disambiguate via a second field (rejected — more state to keep in sync for no benefit over just using an already-unique composed string).

**Benefits**: Composed labels are unique across the full catalog (verified: zero collisions across 119 live products) so selection is unambiguous; the same string appears in the dropdown, the line item, the live preview, and the PDF, so there's never a mismatch between what was selected and what's shown; free-text ad-hoc items are untouched.

**Drawbacks**: Existing saved invoices created before this change keep whatever bare name was captured at the time — unaffected, since `InvoiceItem.name` is a snapshot, not a live join. Going forward, the persisted item name is a few characters longer ("— 1 Box" suffix); judged acceptable since it's factually accurate (`price`/`bulkPrice5`/`bulkPrice10` are all defined per-box).

## 15. Payment arrangements: real relational models, not JSON on Invoice

**Decision**: Added `PaymentArrangement` (1:1 with `Invoice`) and `PaymentArrangementInstallment` (1:many, one row per scheduled payment including the initial one) as real Prisma models, plus `PaymentFrequency` (`WEEKLY`/`BIWEEKLY`) and `InstallmentStatus` (`PENDING`/`PAID`/`OVERDUE` — the last not yet set automatically) enums, rather than a JSON blob on `Invoice` or a set of ad-hoc form fields that don't persist a real schedule.

**Reason**: The feature explicitly asked to be "a reusable data model rather than temporary form fields," naming future needs (overdue detection, reminders, a customer payment portal, partial payment history, audit logs, finance reporting) that all require querying/updating *individual* installments — a JSON blob would mean deserializing and rewriting the whole schedule for any single-row change, and couldn't be indexed or queried by due date across invoices for something like an overdue-detection job.

**Alternatives considered**: `Json` column on `Invoice` holding the schedule array (rejected — exactly the future-features problem above); a single `PaymentArrangement` row with the schedule inline as JSON but installments as their own rows only for *paid* ones (rejected — inconsistent shape between paid/pending installments for no real benefit).

**Benefits**: Each installment is independently queryable/updatable (`WHERE dueDate < now() AND status = 'PENDING'` already answers "what's overdue" the moment that feature is built — no migration needed then). Installment #1 is always the initial payment (generated alongside the arrangement, immediately `PAID`), so the schedule table is one uniform list, not "initial payment info" plus a separately-shaped "future schedule."

**Drawbacks**: Two new tables instead of one JSON column — judged worth it given the explicit future-compatibility requirement.

## 16. Setting up an arrangement doesn't record a new payment — and is available on any invoice with a balance, not just Partial ones

**Decision**: `createPaymentArrangement()` handles two cases. If the invoice already has a payment, "Initial Payment Amount/Date" are derived from its *existing* history (`amountPaid`, and the earliest payment's date) rather than accepted as new input — it never touches `Invoice.amountPaid`/`balanceDue`, since those were already set correctly by whatever payment(s) happened. If the invoice has no payment yet, there's no history to derive from, so the admin instead provides a `startDate` and the *entire* schedule is generated fresh from it, with every installment created `PENDING` (none pre-marked paid). Either way, only `numberOfPayments`, `frequency`, and (when needed) `startDate` are actually submitted — never a payment amount or method.

**Reason**: Initially this only supported the has-a-payment case, gated to invoices already at Partial status, per a literal reading of the original spec ("should not appear for Pending or Paid invoices"). Live use surfaced the gap directly: an admin wanted to set up a plan proactively on a brand-new Draft/Pending invoice with nothing paid yet ("just in case it needs to be utilized," uniformly available like any other invoice) — not only after the fact. Requiring an existing payment first made that impossible. Generalizing to "any invoice with `balanceDue > 0`" and letting the schedule start from a chosen date instead of a derived one covers both real workflows without duplicating the creation logic.

**Alternatives considered**: Keep requiring a prior payment and just tell users to record a token payment first to unlock the section (rejected — forces an artificial workaround for a legitimate use case); always ask for a fresh "Initial Payment Amount" to record regardless of history (rejected — reintroduces the double-counted-payment problem for invoices that already have one, see the previous version of this decision).

**Benefits**: One creation flow covers "already paid something, schedule the rest" and "nothing paid yet, schedule everything" without two separate code paths in the UI beyond which fields are shown; the arrangement still can never drift from `Invoice.amountPaid`/`balanceDue`, since neither case lets the client submit its own payment numbers — only a start date and a payment count.

**Drawbacks**: If an invoice received multiple separate payments before the arrangement was set up, "Initial Payment Date" is the *earliest* of them (not a specific single transaction) — judged acceptable since the summary is about the amount, and the schedule's dates all key off that one anchor date regardless.

## 17. Payment Status (Pending/Partial/Paid) is computed, not stored

**Decision**: `computePaymentStatus(amountPaid, total)` in `lib/invoice/paymentArrangement.ts` derives Pending/Partial/Paid from the invoice's existing `amountPaid`/`total` fields at render time — it isn't a new database column, and it's separate from (and doesn't touch) the existing `InvoiceStatus` enum (`DRAFT`/`PENDING`/.../`PAID`/`PARTIALLY_PAID`/etc.), which continues to drive the admin's own workflow state and what shows on generated PDFs.

**Reason**: The three states' definitions ("no payment received," "one or more payments received but a balance remains," "balance satisfied") are objective facts already fully determined by existing fields — storing a second value for the same fact would be exactly the kind of value that could drift from reality. `InvoiceStatus` already has its own `PAID`/`PARTIALLY_PAID` values serving a different purpose (overall workflow/document state, manually set via `InvoiceStatusSection`) — collapsing it down to only these three values would delete `DRAFT`/`APPROVED`/`ISSUED`/`CANCELLED`/`REFUNDED`/`VOID`, breaking the just-built invoice-status workflow control for no reason connected to this feature.

**Alternatives considered**: Repurpose `InvoiceStatus` itself to mean this (rejected — would destroy unrelated, already-working workflow-state functionality); add a stored `paymentStatus` column (rejected — redundant with data that already exists, risking drift).

**Benefits**: Always accurate by construction; gates the Payment Arrangement section's "offer to create" state (`Partial` + no existing arrangement) without needing to keep a separate flag in sync.

**Drawbacks**: None identified.

## 18. PDF layout tightened to fit a typical invoice on one page; legal footer's `wrap` moved from the whole block to each clause

**Decision**: Reduced page margins (48pt → 28pt), the header logo (240×161 → 140×94), and nearly every section's internal spacing/padding across `lib/invoice/pdf/shared.tsx`, so a typical invoice (a few items, a payment history or arrangement, the legal footer) fits on one LETTER page. Also: the Master Invoice no longer renders a separate "Payment History" table when a payment arrangement exists (its own schedule table already lists every payment as "Payment N," so showing both repeated the same rows and cost real estate for nothing). Separately, `LegalFooter`'s `wrap={false}` moved from the outer footer container to each individual legal clause (`legalSection`) — the footer itself can now split across a page boundary if it must, but a clause never splits mid-paragraph.

**Reason**: The branding pass had made the header logo large and generous section spacing, without checking whether real content fit on one page — a live invoice with a payment history and a 4-installment arrangement was overflowing to 2 pages, and root-causing it found the actual bug: the *whole* legal footer had `wrap={false}`, so whenever it was even a few points short of fitting in the remaining space on page 1, react-pdf pushed the *entire* footer (divider, tagline, both legal paragraphs) to page 2 rather than using the space that was there — producing a second page that was nearly empty except the fine print. That's a strictly worse failure mode than needing a second page for genuine content overflow (items, notes, a long arrangement schedule), which is expected and fine.

**Alternatives considered**: Keep `wrap={false}` on the whole footer and just shrink everything further to always avoid triggering it (rejected — chasing this for arbitrarily heavy content, like an invoice with full contact info plus two long note paragraphs plus a 4-installment arrangement, has diminishing returns and would eventually make the *typical* invoice look cramped just to accommodate rare edge cases); let the footer wrap freely with no `wrap` constraint anywhere (rejected — risks a clause's heading landing on one page and its body on the next, which reads as broken).

**Benefits**: Verified empirically (rendering real and representative mock invoices, counting actual PDF page objects): every "typical" scenario tested — no arrangement, one payment, one payment plus a 4-installment arrangement (matching the real Marvin Alexander invoice) — now renders on exactly one page for both the Master Invoice and Client Invoice. A deliberately extreme case (full customer contact fields, two long note paragraphs, an arrangement, discounts) still uses 2 pages, but only because page 1 is already genuinely full of real content — the footer following onto page 2 in that case is legitimate overflow, not an isolated disclaimer stranded for no reason.

**Drawbacks**: The header logo and body text are noticeably smaller than the previous branding-focused sizing. Judged an acceptable trade against the explicit "must fit on one page" requirement — still sized as a clear, legible brand mark, just not the maximal size the earlier pass used.

## 19. ZIP auto-population via a keyless third-party API; "same as billing" is ephemeral UI state, not a persisted field

**Decision**: Added `GET /api/admin/zip-lookup` — an admin-gated server proxy to Zippopotam.us (`https://api.zippopotam.us/us/{zip5}`) — and a shared `useZipLookup` client hook consumed identically by `CustomerInfoSection` (billing) and `ShippingSection` (shipping). Entering a complete 5-digit ZIP (a ZIP+4 suffix is tolerated, only the first 5 digits are looked up) auto-fills city/state while leaving both editable; a failed lookup shows an inline message and never clears existing address data. Separately, `ShippingSection` gained a "Same as billing address" checkbox and `InvoiceBuilder` gained a `shippingSameAsBilling` boolean `useState` — deliberately **not** part of `InvoiceDraft` or the save payload. While checked, editing billing address fields also copies into `draft.shipping.shippingAddress` in the same `setDraft` call (no `useEffect`), and the shipping address sub-fields render disabled; unchecking leaves the last-copied values in place as an independent starting point rather than clearing them.

**Reason**: Zippopotam.us was chosen specifically because it's free and keyless — provisioning a credentialed service (e.g. the USPS Web Tools API) isn't something an agent can do on the user's behalf, and the spec didn't require a specific provider. Proxying server-side (rather than calling it directly from the browser) keeps the third-party dependency swappable and puts it behind the same `isAdmin` gate as every other invoice-admin endpoint. The same-as-billing flag is UI convenience only — the data that actually needs to persist is the shipping address values themselves, which flow through the existing `draft.shipping` save path unchanged; there's no server-side concept of "linked" addresses to keep in sync later, matching how `paymentStatus` (#17) is also computed/ephemeral rather than stored.

**Alternatives considered**: A signed-up-for lookup provider (rejected — requires credentials this project doesn't have and an agent can't obtain); storing `sameAsBilling` as a persisted `Invoice` column (rejected — would require migrating existing invoices and gives the flag meaning it doesn't need; the copied address values are self-sufficient on their own once saved); syncing shipping from billing via a `useEffect` watching `draft.customer` (rejected — this codebase avoids `useEffect`-driven cross-field sync, per prior `react-hooks/set-state-in-effect` friction; a direct copy inside the existing `onChange` handler is simpler and has no render-order surprises).

**Benefits**: New invoices get city/state for free from a ZIP, cutting a common data-entry error (typoed or mismatched city/state/ZIP combinations). The same-as-billing checkbox removes the most common redundant retyping in the builder without adding any new persisted schema or migration risk. Existing invoices (saved before this feature existed) load unaffected — `street2` was already optional in both the type and the zod schema, so old records without it just render an empty field.

**Drawbacks**: Zippopotam.us is a third-party dependency with no SLA; a failed or slow lookup degrades gracefully (manual entry still works, existing data is never cleared) but isn't retried automatically. The same-as-billing flag resets to unchecked on every page load/reload (it's not persisted), so a user editing a saved invoice with billing == shipping by coincidence won't see the checkbox pre-checked — judged acceptable since the checkbox is a data-entry shortcut, not a fact about the invoice.

## 20. Delete is a new `deletedAt` column and Trash view, separate from the existing `archivedAt` Archive feature

**Decision**: Added `Invoice.deletedAt DateTime?`, distinct from the existing `archivedAt`. "Archive" (#unnumbered, pre-dates this decision log) is for a completed invoice you keep around for records — still fully visible via `includeArchived`. "Delete" is for "get this off my list, I probably don't need it" — it drops out of every normal view immediately and only lives in a dedicated `/admin/invoices/trash` page, with two actions: Restore (clears `deletedAt`) or Delete Forever (an actual `prisma.invoice.delete()`, cascading to items/discounts/payments/payment arrangement). `permanentlyDeleteInvoice()` refuses to run unless `deletedAt` is already set — the "trash first, then a separate final action" two-step is enforced at the data layer, not just hidden behind two button clicks in the UI. Both the initial Delete button and the Trash page's Delete Forever button use an in-page two-click confirm (arm on first click, 4s window, second click executes) rather than a native `confirm()` dialog, matching this UI's existing toast-driven conventions.

**Reason**: User request: "there needs to be an option to delete an invoice and it go into a holding spot for a secondary and final delete in case of an accidental delete, it can be recovered." Reusing `archivedAt` for this would conflate two different intents (a keeper vs. a mistake) and break the existing Archive/Restore UI's assumption that an archived invoice is a real, complete record.

**Alternatives considered**: Overloading `archivedAt` with a second flag distinguishing "archived" from "deleted" (rejected — two independent boolean-ish states are clearer as two independent nullable timestamps than one column with contextual meaning); immediate hard delete with no holding period (rejected — directly contradicts the explicit "recoverable" requirement); a native `window.confirm()` for the permanent-delete step (rejected — inconsistent with the rest of the dashboard, which has no native browser dialogs anywhere, and reads as a jarring UX regression against the app's otherwise consistent dark-themed, toast-driven interaction pattern).

**Benefits**: Accidental deletes are recoverable right up until someone deliberately visits Trash and confirms Delete Forever twice. Cascading FK `onDelete: Cascade` was already in place on every child table (items, discounts, payments, payment arrangement + installments) from the original schema design, so the hard-delete path needed no schema changes beyond the new `deletedAt` column itself.

**Drawbacks**: Trash has no auto-purge — an invoice sits there indefinitely until an admin manually empties it. Acceptable for now given invoice volume is low; worth revisiting (a scheduled sweep) if Trash ever accumulates enough rows to matter.

## 21. Automated Paid → Archived transition after a configurable number of days, driven by a daily Vercel Cron sweep

**Decision**: Extended the existing manual Archive feature with an automatic path: once an invoice's `status` is `PAID`, a background sweep (`GET /api/cron/archive-invoices`, run daily via Vercel Cron, `Authorization: Bearer CRON_SECRET`) archives it (`archivedAt = now`) once `paidAt` is older than the configured `archiveAfterDays` (default 30; 60/90/never also supported). The setting lives in a new one-row `InvoiceSettings` table (fixed id `'singleton'`), editable from a new `Settings → Invoices` page. `paidAt` is now actively maintained rather than "set once": `updateInvoice` recomputes `isPaid = payload.status === 'PAID' && balanceDue <= 0` on every save and sets `paidAt` to *now* whenever that's true (so editing a still-paid invoice resets the countdown, per spec) or clears both `paidAt` and `archivedAt` the moment it isn't (reopened, balance increased, status moved off PAID — un-archiving it too, since a no-longer-fully-paid invoice shouldn't stay hidden in Archived). `recordPayment` already refreshed `paidAt` to now on every transition into fully-paid, so the "additional payment" reset trigger needed no change there. The invoice list's status dropdown was replaced with a `filter` param — `all | outstanding | paid | overdue | archived` — mapped to `buildFilterClause()` in `lib/invoices.ts`, which also excludes trashed (`deletedAt`) invoices consistent with decision #20; a search term ignores the current filter and searches active + archived together, per the spec's "search both" requirement.

**Reason**: User request for QuickBooks/Stripe/Shopify-style automatic archival, driven by a configurable delay, with every listed reset trigger (edit, reversal, refund, reopen, additional payment, balance change) restarting the countdown — modeled as "recompute `paidAt` on every relevant write" rather than a separate mutable "archive date" field, so there's exactly one source of truth for when the countdown started and no way for it to drift out of sync with the invoice's actual payment history.

**Alternatives considered**: A `nextArchiveAt` field computed and stored at payment time (rejected — redundant with `paidAt + archiveAfterDays`, and could drift from `paidAt` if the setting changes after the invoice was paid — computing at sweep time always uses the *current* setting); an in-process `setTimeout`/cron-in-Node scheduler (rejected — this app is deployed as Vercel serverless functions with no persistent long-running process to host a timer; hitting an API route via Vercel Cron is the standard pattern here); computing archived-vs-active on every read instead of writing `archivedAt` (rejected — the spec explicitly asks for an actual flag flip, and a stored flag keeps the existing `archivedAt`-based list filtering/search/reporting index-friendly instead of computing a date comparison on every row on every request); keeping the old raw `InvoiceStatus` dropdown alongside the new All/Outstanding/Paid/Overdue/Archived filter (rejected — two overlapping filter UIs on the same table read as confusing; the new set covers what the spec asks for, and "All" still surfaces every non-archived status).

**Benefits**: Reuses the entire existing Archive infrastructure (list filtering, restore, still fully searchable/viewable/exportable/PDF-able — none of that changes for an auto-archived invoice vs. a manually archived one, since it's the same `archivedAt` column). No new archival code path for reporting/PDFs/search to keep in sync. The dashboard's Revenue KPI now includes archived invoices (previously excluded) since a fully-paid, auto-archived invoice's revenue is exactly as real as an active one's; outstanding balance and the operational KPIs (pending shipments, delivered) stay scoped to active invoices since those describe current workflow state.

**Drawbacks**: "Overdue" as a filter has no natural definition on this data model — there's no due-date field on `Invoice` itself (only `PaymentArrangementInstallment.dueDate` for installment plans). Implemented as a pragmatic stand-in (`balanceDue > 0` and `issuedAt` more than 30 days ago, independent of the configurable archive delay) rather than leaving the filter out; this is the one real assumption in this feature and is worth revisiting if a true per-invoice due date is ever added. Vercel's cron scheduling grain is daily, not real-time — an invoice can sit up to ~24h past its exact archive moment before the sweep catches it, immaterial at a 30+ day granularity. `CRON_SECRET` must be set in Vercel's project environment variables (Production and Preview) for the deployed cron trigger to authenticate — not something this session can do on the user's behalf, so it's called out as a manual deployment step.

## 22. Carrier-agnostic shipment tracking built on Shippo (already an existing dependency), with a `ShippingProvider` abstraction so it isn't hard-coded to one API

**Decision**: Added a full tracking subsystem under `lib/tracking/` behind a `ShippingProvider` interface (`registerTracking`, `getTrackingStatus`, `verifyWebhook`, `normalizeWebhookPayload`) — `shippoProvider` is the only implementation today, resolved per-carrier through `registry.ts` so a future direct-carrier adapter (or a different multi-carrier vendor) only needs a new adapter file plus one line in the registry; nothing in invoice code, the UI, or the webhook/cron routes would need to change. Chose Shippo specifically because it's already a dependency (`lib/shippo.ts`, used today for Order shipping-label purchases) and is itself a multi-carrier aggregator covering USPS/UPS/FedEx/DHL and more under one API — exactly the "prefer a multi-carrier API" guidance, with zero new third-party accounts to provision. New Prisma models: `Shipment` (1:1 with Invoice, the current tracking state), `TrackingEvent` (append-only history, deduped via a `(shipmentId, eventHash)` unique constraint), `ShipmentNotification` (email send history), and `InvoiceActivityLog` (a dedicated shipment/tracking-focused activity log, deliberately separate from the existing admin-action-shaped `AdminAuditLog`, since this one needs an optional `userId` to cover webhook/polling/system-sourced entries). Every carrier event is normalized into a fixed 16-value `ShippingStatus` enum, while the original carrier text is always preserved alongside it (`TrackingEvent.carrierStatus`/`description`), never discarded. A new `InvoiceOrderStatus` enum (`OPEN/IN_PROGRESS/COMPLETED/CANCELLED`) implements the spec's completion rule (`computeOrderStatus()` in `lib/tracking/orderStatus.ts`, a pure function callable from both the payment side and the shipping side) as its own 4th status dimension, independent of the existing `InvoiceStatus` (payment) and `deliveryStatus` (legacy fulfillment, left untouched for back-compat — the new `shippingStatus` field is what the tracking system actually drives, with a lookup table keeping the old field in a sensible state too). Webhooks (`/api/webhooks/shippo`) are the primary update path; a daily-quantized polling cron (`/api/cron/poll-tracking`, `CRON_SECRET`-gated like the archive sweep) is the fallback for shipments that miss one, with retry/backoff and per-shipment failure isolation so one bad shipment never blocks the batch.

**Reason**: The spec explicitly asks for a carrier abstraction ("do not place carrier-specific logic directly inside the invoice component") and prefers a multi-carrier API "to reduce duplicated carrier logic" — Shippo satisfies both without adding a new vendor relationship, since it's the exact tool this codebase already trusts for label purchases. The dedicated `InvoiceActivityLog` (rather than folding shipment events into `AdminAuditLog`) exists because the spec's activity-log shape (previous/new value, carrier, tracking number, and a `source: Manual|Webhook|Polling|System` with an *optional* user) doesn't fit `AdminAuditLog`'s admin-action shape (mandatory `adminId`, generic `details: Json`) — reusing it would mean either fabricating a fake admin id for system-sourced events or loosening a constraint that's correct for every other use of that table.

**Alternatives considered**: Direct per-carrier APIs (USPS Web Tools, UPS/FedEx/DHL developer APIs) instead of Shippo (rejected — 4 separate credentialed integrations instead of 1, each with its own auth/rate-limit/webhook quirks, for no benefit over the multi-carrier aggregator the spec itself recommends); folding shipment tracking into the existing `ShippingLabel` model (rejected — `ShippingLabel` is a 1:1, Order-only, purchase-transaction snapshot with no history/versioning concept; invoices don't have Orders in the manual-sale case this whole invoice module exists for, and a tracking timeline is a fundamentally different shape than a label receipt); a single combined `orderStatus`/`shippingStatus` field (rejected — the spec is explicit that payment/shipping/fulfillment/order must stay separate dimensions, and collapsing any of them back together would silently violate the "do not mark an invoice paid merely because a package was delivered" rule).

**Benefits**: Adding a new carrier (or swapping providers) never touches `TrackingSection.tsx`, the webhook route, the cron route, or `service.ts`'s orchestration logic — only `registry.ts` and a new file implementing `ShippingProvider`. The event-hash dedup constraint is enforced at the database layer (a duplicate webhook or overlapping poll fails the unique constraint and is caught, not re-processed), not just by application-level bookkeeping that could drift. `computeOrderStatus()` being a pure function meant the paid+delivered completion rule (and its unpaid+delivered non-completion counterpart) could be verified with plain unit tests with no database at all.

**Drawbacks**: Shippo doesn't sign webhook payloads with an HMAC secret the way Stripe does — the auth boundary here is a shared-secret token embedded in the webhook URL itself (`?token=<SHIPPO_WEBHOOK_SECRET>`), which is weaker than true signature verification (a leaked URL is a leaked secret) but is Shippo's own documented pattern for this exact problem. The project's configured `SHIPPO_API_KEY` is a sandbox/test-mode key, which only accepts Shippo's fake `'shippo'` test carrier for tracking registration (confirmed empirically — a real `USPS`/`UPS`/etc. token is rejected with `"usps is not a valid test tracking carrier"`); this is a Shippo sandbox-mode limitation, not a bug in the adapter, but it does mean the real registration path against live carriers couldn't be exercised end-to-end in this environment — verified instead via direct calls to `processTrackingEvents`/`computeOrderStatus` with synthetic events, and the full error-handling path was confirmed live (the sandbox rejection surfaces correctly as a toast in the UI). Vercel Cron on the Hobby plan only supports daily schedules; the `poll-tracking` cron is configured for every 4 hours (`0 */4 * * *`), which requires a Pro-plan project to actually run at that cadence — on Hobby it will silently run at whatever cadence Vercel allows instead, which is a deployment-environment fact this session can't change, only flag.

## 23. Automatic "invoice issued" customer email, gated by activity-log presence rather than a boolean flag

**Decision**: The first time an invoice reaches `ISSUED`, `PAID`, or `PARTIALLY_PAID` — checked from all three places that can cause that transition (`createInvoice`, `updateInvoice`, `recordPayment` in `lib/invoices.ts`) — `sendInvoiceIssuedEmailIfNeeded()` (`lib/invoiceIssuedEmail.tsx`) emails the Client Invoice PDF to `customerEmail`, if one is on file and `InvoiceSettings.autoEmailInvoiceOnIssue` is enabled (default on). Whether the one-time send has already happened is determined by querying `InvoiceActivityLog` for an existing `INVOICE_ISSUED_EMAIL_SENT` row for that invoice — not a separate boolean column — so a later manual resend (the new "Email Invoice to Customer" button, `sendInvoiceEmailManually()`, always sends regardless of this check) can never be mistaken for "the auto-send hasn't fired yet." Denormalized `lastInvoiceEmailSentAt`/`Status`/`FailureReason` columns on `Invoice` mirror the existing `lastNotification*` pattern from the tracking system, for quick display without a join.

**Reason**: Requested directly — invoices should sync to the customer automatically on the basics (issued, payment status, arrangement schedule, tracking once added) without requiring an admin to remember to click "download PDF" and attach it to a manual email every time, while keeping the existing manual PDF-download/send workflow fully available as a fallback or for ad-hoc resends.

**Alternatives considered**: A boolean `invoiceEmailSent` flag on `Invoice` (rejected — indistinguishable from "manually resent since," which would make a legitimate resend look like the auto-send already happened, silently suppressing it if a status ever reverted and re-advanced); firing only from `updateInvoice` (rejected — `recordPayment` can independently drive a `DRAFT` invoice straight to `PAID`/`PARTIALLY_PAID` without ever passing through an explicit "Save" on `ISSUED`, which would silently skip the customer email for that path).

**Benefits**: Reuses the exact Client Invoice PDF generation and Resend-attachment pattern already proven out in `lib/tracking/notifications.tsx`, so there's no new PDF-rendering or email-delivery code to trust. The trigger check is a single pure predicate (`isInvoiceEmailTriggerStatus`), unit-testable with no database.

**Drawbacks**: `RESEND_FROM_EMAIL` is still Resend's own sandbox default (`onboarding@resend.dev`) rather than a verified Pepscore domain, since domain verification was intentionally tabled — every automatic email (this one and the tracking notifications) sends from that address until a custom domain is verified and the env var updated, which is an operational follow-up, not a code change.

## 24. `Shipment` becomes a true one-to-many under `Invoice`, with a derived (never stored) primary shipment, plus a centralized Fulfillment Gate for label purchase

**Decision**: Dropped the `@unique` constraint on `Shipment.invoiceId` (`Invoice.shipment Shipment?` → `Invoice.shipments Shipment[]`) so an invoice can have any number of shipments — a manually-typed tracking number, a purchased label, a replacement after a mistake, a returned package — each its own permanent row. Nothing is ever deleted, including voided shipments. Which shipment is "current" is never a stored pointer; `lib/shipments/primary.ts`'s `getPrimaryShipment()` derives it on read (most recent non-voided, falling back to the single most recent if every shipment is voided), and `Invoice`'s denormalized fields (`shippingStatus`, `trackingNumber`, etc., used for quick list/PDF display) are refreshed from whichever shipment is currently primary — a status update landing on a superseded/voided shipment never overwrites what the invoice shows. Alongside this, real Shippo label purchase was added (`lib/fulfillment/labels.ts`, reusing the existing `lib/shippo.ts` client built for storefront Orders) gated by a new centralized Fulfillment Gate (`lib/fulfillment/gate.ts`'s `checkFulfillmentEligibility()`): a shipment may be created when the invoice is paid in full, OR has an active payment arrangement, OR carries a manual override. The override is a permanent, attributed record (`Invoice.fulfillmentOverrideAt/By/Note`, set only via `overrideFulfillmentEligibility()`), not a plain boolean, and both the invoice and customer activity timelines log it.

**Reason**: Requested directly, with two explicit constraints from the outset: (1) real physical packages for one invoice are not always exactly one shipment — a mis-typed tracking number, a split package, or a replaced label are all legitimate, recurring cases that a hard 1:1 model can't represent without either overwriting history or bolting on a parallel log table later; (2) a shipping label is real money spent through Shippo, so "is this invoice allowed to ship" needed to be one function checked in exactly one place — never trusting a client-side-only check, and never re-implemented slightly differently in a second call site later.

**Alternatives considered**: Keeping `Shipment` 1:1 and adding a separate `ShipmentHistory`/`ShipmentLabel` log table for anything beyond "the current shipment" (rejected — introduces two tables representing overlapping information, and every consumer of shipment data would need to know which one is authoritative for what); storing a `primaryShipmentId` pointer on `Invoice` instead of deriving it (rejected — a stored pointer can silently drift out of sync with reality, e.g. if a shipment is voided without the pointer being reassigned, whereas a pure derivation function is always correct by construction and is unit-testable with no database); scattering the "can this ship" check inline into the UI component and the purchase API route separately (rejected — exactly the kind of duplicated business rule that drifts the moment one call site is updated and the other isn't, for a check that gates spending real postage money).

**Benefits**: Every existing consumer of the old singular `invoice.shipment` (`lib/tracking/service.ts`, `lib/tracking/notifications.tsx`, the PDF's `ShipmentTrackingSection`, the admin tracking API route) was migrated by following `tsc --noEmit` compile errors as an exhaustive checklist, so nothing was missed silently. The Fulfillment Gate being one pure function (`computeFulfillmentEligibility`) plus one thin database-fetching wrapper (`checkFulfillmentEligibility`) meant the override-priority ordering (manual override beats paid-in-full beats active-arrangement beats nothing) could be verified with plain unit tests. Label purchase deliberately writes nothing to the database until Shippo confirms success, so a failed purchase never leaves a partial `Shipment` row, and the admin's entered package form is left untouched in local component state for an easy retry.

**Drawbacks**: `Shipment`'s label-purchase-specific fields (`shippoShipmentId`, `postageAmount`, `labelUrl`, weight/dimensions, etc.) are `null` for manually-entered tracking (`origin: MANUAL_ENTRY`) and only populated for a purchased label (`origin: LABEL_PURCHASE`) — a wider table than either use case alone needs, accepted since the two origins share every other field (carrier, tracking number, status, notifications) and a separate table per origin would have meant duplicating all of that tracking/notification machinery twice. Per-shipment UI actions (voiding, refreshing, resending an email for a *specific* non-primary shipment) were deliberately scoped to only the primary shipment for v1 — every shipment is visible and preserved, but only the current one has the full action set; expanding that is straightforward later since the data model already supports it.

## 25. Manual tracking is Shippo-independent; backorder gating extended to every path that can move an invoice's shipping status, not just label purchase; line-item partial shipment deliberately deferred

**Decision**: `addTrackingToInvoice()` (manual "Add Tracking") no longer fails when Shippo can't register the tracking number (missing/invalid `SHIPPO_API_KEY`, Shippo account issue) — the provider call is now best-effort, wrapped in try/catch, surfaced as a non-fatal `providerWarning` in the response. The tracking number, carrier-built tracking URL (`buildCarrierTrackingUrl()`, already Shippo-independent), and `Shipment` row all save regardless. Separately, the Fulfillment Gate's backorder check — previously only enforced on Shippo label purchases via `checkFulfillmentEligibility()` — is now also enforced (a) at manual tracking creation (`addTrackingToInvoice`, via the narrower `isTrackingBlockedByBackorder()`, which unlike the full gate never checks payment status) and (b) inside `processTrackingEvents()`, the shared cascade every webhook, poll, manual refresh, "Mark Delivered," and "Override Status" action ultimately runs through. When a primary shipment's new status would move the invoice's customer-facing `deliveryStatus` past Preparing/Packed while a backorder is active, the `Shipment`/`TrackingEvent` rows still update (the real carrier fact is never hidden), but the invoice's own `shippingStatus`/`deliveryStatus`/`orderStatus` fields and the customer notification email are held back, and a `SHIPPING_STATUS_UPDATE_SUPPRESSED_BY_BACKORDER` activity-log entry records it. The two purely-admin-intent actions (`markDeliveredManually`, `overrideShippingStatus`) throw a `BackorderBlocksTrackingError` instead of silently no-opping, so the admin sees why nothing happened rather than a false "success" toast; the automated webhook/poll paths suppress silently since there's no one waiting on a click. The existing `fulfillmentOverrideAt` override is the one escape hatch everywhere.

Also assessed and deliberately deferred: true line-item partial shipment (tracking which specific `InvoiceItem`s are in which `Shipment`). The existing one-to-many `Shipment` model (Decision 24) already lets an invoice have several shipments — e.g. one box now, a second later — which covers "the order shipped in parts" at the invoice level. What it doesn't do is record which line items went in which box. Building that properly needs a `ShipmentItem` join table (`shipmentId`, `invoiceItemId`, `quantity`) plus UI to assign items to a shipment at tracking-entry time — a real, additive schema change, not something to fake with a free-text note on the shipment (notes/labelSource, above, are for admin context, not a substitute for structured data). Deferred because nothing in the current real-world workflow (Pirate Ship, single-box orders) needs it yet; flagged here so it isn't silently forgotten if/when a genuinely split, multi-box order needs to be represented precisely.

**Reason**: The manual-tracking Shippo dependency was a real production bug — a hard `throw` inside a provider adapter meant to be optional broke the one fulfillment path (Pirate Ship) actually used day-to-day. The backorder-gating extension follows directly from the existing Fulfillment Gate's own stated principle (Decision 24): "is this invoice allowed to ship" should be one check, enforced everywhere shipping can actually progress — not just the money-spending Shippo path. Leaving `processTrackingEvents()` ungated would have meant a backorder added *after* a shipment already existed had no effect on what the customer sees, which contradicts "active backorder keeps customer-facing fulfillment at Preparing."

**Alternatives considered**: Blocking `processTrackingEvents()` from writing to `Shipment`/`TrackingEvent` at all while backorder-blocked (rejected — a real carrier event is a fact; hiding it from the shipment's own history would make troubleshooting a delayed backorder resolution harder, not easier, and breaks the "nothing is ever discarded" precedent from Decision 24). Making manual tracking's provider registration a hard prerequisite with a friendlier error message instead of best-effort (rejected — the whole point of Pirate Ship/manual workflows is that Shippo involvement is optional, not just better-explained-when-missing). Silently no-opping `markDeliveredManually`/`overrideShippingStatus` under an active backorder, matching the webhook path (rejected — those two are explicit single clicks with an expected effect; a webhook has no one watching for a result, an admin action does).

**Benefits**: One rehearsal-verified behavior everywhere shipping status can move, instead of a gate that only covered the code path someone happened to test. Manual tracking is now genuinely first-class rather than "works if Shippo happens to also be configured."

**Drawbacks**: `processTrackingEvents()`'s signature changed from `Promise<void>` to `Promise<{ invoiceCascadeSuppressed: boolean }>` — every existing caller was checked (webhook route, poll cron, the two admin actions) and updated or confirmed safe to ignore the new field. Line-item partial shipment remains unbuilt; an order that's genuinely split across boxes today is only representable at the "which shipments exist" level, not "which items are in which shipment," until that's built.

## 26. Printerless USPS QR-code labels built and verified against Shippo's real test API; live purchasing gated behind an explicit kill-switch while the account is held for Trust & Safety review

**Decision**: `lib/shippo.ts`'s `getRates()` now always sends `extra.qr_code_requested: true` on every shipment/rate-shopping call — harmless for carriers that don't support one (Shippo just omits `qr_code_url` from the eventual purchase response; `label_url` is always still returned regardless, so the printable fallback is never lost). `Shipment.qrCodeUrl`/`qrCodeRequested` (additive) capture the result; the UI shows the QR code prominently (full-screen, downloadable, reopenable from the invoice) when present, or an explicit "this service doesn't support QR codes" notice when requested but not returned — never a silent PDF-only fallback. This was verified with a real Shippo test-mode purchase against the new `orders@pepscorelab.com` account: USPS Ground Advantage genuinely returned a working `qr_code_url`. That same testing surfaced a real, separate bug — `purchaseLabel()` only checked HTTP status, but Shippo can return `201` with `status: "ERROR"` in the body (purchase actually failed) — now fixed to check the body's own status and surface the real message.

Separately: Pepscore's Shippo account is currently held pending Trust & Safety business-registration verification (the account doesn't yet have the paperwork Shippo requires). Rather than let a technically-still-functional test-mode key create ambiguity in production — an admin could otherwise purchase a real-looking-but-fake test label and mistake it for a live one — `isShippoPurchasingEnabled()` (`lib/fulfillment/labels.ts`) is an explicit, separate kill-switch (`SHIPPO_PURCHASING_ENABLED=true`, unset = off) checked before *both* rate-shopping and purchase, independent of whether a key happens to be configured. The "Create Shipping Label" panel proactively shows the deferred-account message (via the existing `/fulfillment/eligibility` endpoint, extended with `shippoPurchasingEnabled`/`shippoDeferredMessage`) rather than only surfacing it as a toast after the admin fills in the whole form. Manual tracking (`lib/tracking/service.ts`'s `addTrackingToInvoice`) is entirely unaffected by this switch — it was already Shippo-independent per Decision 25, and stays the actual production shipping workflow (Pirate Ship + manual entry) until the account is approved.

**Reason**: The QR-code feature was requested and is fully built/tested against the real API — no reason to hold that work back. But *purchasing* (even test-mode) needed a harder stop than "the account happens to still have an old key" once the decision was made to defer live activation — a stale key silently continuing to "work" would be exactly the kind of ambiguity that leads to a real mistake later.

**Alternatives considered**: Detecting live-vs-test by inspecting the key's own prefix (`shippo_live_` vs `shippo_test_`) instead of a separate flag (rejected — conflates two different questions: "is this key live" and "are we ready to let admins purchase with it," which won't always move together, e.g. wanting to keep testing against a live key in a controlled way before flipping purchasing on for real). Removing the `SHIPPO_API_KEY` env var entirely instead of adding a flag (rejected — manual tracking's provider registration still uses it opportunistically per Decision 25, and removing it would just make that best-effort path fail instead of succeed harmlessly).

**Next steps once Pepscore's business registration is available**: complete Shippo's Trust & Safety review with real documentation (never submit incomplete/inaccurate info to bypass it), request and install a live API key, add a payment method, fix `FulfillmentSettings.returnAddress`'s missing phone/email (USPS requires both — found live during this session's testing), register a Production-environment webhook (a Test-environment one already exists, pointing at the same endpoint), then flip `SHIPPO_PURCHASING_ENABLED=true` in Vercel. No code changes should be needed at that point — everything described above already works, confirmed against the real API in test mode.

## 27. SMS opt-out is a real, DB-backed customer state (not just a Twilio console setting), verified end-to-end against a genuinely-computed Twilio signature; A2P 10DLC registration itself stays a pure owner checklist

**Decision**: Audited the existing SMS infrastructure (`lib/notifications/bestEffortSms.ts`, `sendCategorizedSms`) and found it already genuinely complete on the sending side — a real `twilio` SDK call (lazily imported so `TWILIO_*` is never required at module-load/build time), E.164 normalization, and a `Communication` row recorded for every attempt including skipped/failed ones. What was missing was the *receiving* half: nothing recorded an inbound STOP/START reply anywhere in Pepscore's own data, and nothing checked such a record before sending. Added `Customer.smsOptedOut` (additive, default `false`) plus `app/api/webhooks/twilio/route.ts` — the inbound "a message comes in" webhook, authenticated by validating Twilio's own `X-Twilio-Signature` header against `twilio.validateRequest()` (fails closed with a 404 if `TWILIO_AUTH_TOKEN` isn't set, since there's no way to verify authenticity without it). A recognized `STOP`/`STOPALL`/`UNSUBSCRIBE`/`CANCEL`/`END`/`QUIT` sets `smsOptedOut = true`; `START`/`YES`/`UNSTOP` reverses it; anything else is a no-op. Both paths log a `CustomerActivityLog` entry (`SMS_OPTED_OUT`/`SMS_OPTED_IN`, `source: WEBHOOK`) and are idempotent (a repeat STOP writes no second log entry). `sendCategorizedSms` now checks this flag immediately before every attempt — but only suppresses a send when the destination phone number actually *is* the referenced customer's own phone (`lib/notifications/phoneMatch.ts`'s digit-sequence comparison, since `Customer.phone` is stored exactly as typed with no normalization). This distinction matters concretely: several SMS call sites pass `context.customerId` on an alert that's actually being sent to an *admin's* phone (e.g. `notifyAdminPaymentSelectionPending`) — that customer's own opt-out must never silently suppress a staff notification that merely references them. Also added the same "Reply STOP to opt out of texts." language already used in `PortalInvite`'s SMS to the four other client-facing transactional SMS bodies in `paymentWorkflow.ts` and `invoiceIssuedEmail.tsx` that were missing it (admin-facing alert bodies in the same file were deliberately left alone — they go to staff, not customers).

**Reason**: Requested directly as A2P 10DLC production-readiness work — carriers and Twilio's own campaign-registration review expect consistent opt-out language across submitted message templates and a working, verifiable STOP/START flow, not just reliance on Twilio's carrier-level Advanced Opt-Out (which blocks future carrier delivery but doesn't tell *Pepscore's own database* that a customer opted out, so an admin reviewing that customer's profile, or a future campaign send, would have no idea).

**Alternatives considered**: Relying solely on Twilio's carrier-level Advanced Opt-Out with no app-side record (rejected — leaves no visibility on the customer profile or in `Communication` history, and gives `sendCategorizedSms` nothing to check before attempting a send that Twilio would silently drop anyway, wasting the attempt and muddying delivery-outcome reporting). Storing a normalized-phone column and matching exactly instead of a digit-comparison helper (rejected as unnecessary scope for now — `findCustomerByPhoneFlexible`'s full-table digit comparison is correct and fast enough at today's customer count; flagged in its own comment as the thing to revisit if that stops being true, not silently deferred). Sending Pepscore's own TwiML auto-reply text on STOP/HELP (rejected — the webhook returns empty TwiML deliberately, since exact required auto-reply copy is part of what gets configured in the Twilio Messaging Service console during A2P registration, not something to hardcode ahead of that review).

**Benefits**: Verified with a real computed Twilio request signature (`twilio.getExpectedTwilioSignature`), not a mocked auth check — the rehearsal script called the actual exported route handler with a genuinely valid signature, an invalid one, and an unconfigured-token case, so signature verification is proven to actually work rather than assumed. The customer-vs-admin-phone distinction in `sendCategorizedSms` was specifically regression-tested (an admin alert referencing an opted-out customer is confirmed NOT suppressed), which is exactly the kind of bug that would otherwise silently break staff notifications months later.

**Drawbacks**: `findCustomerByPhoneFlexible` fetches every customer with a non-null phone and compares in application code rather than filtering in SQL, since stored phone punctuation defeats a plain `contains`. Fine at Pepscore's current scale; would need a normalized-phone column (and index) if the customer table grows large enough for this to matter.

## 28. Payment-provider abstraction, Phase 1 — the existing Stripe integration moved behind a `PaymentProviderAdapter` interface, not rewritten

**Decision**: Audited the existing storefront payment path (`lib/stripe.ts`, `app/api/checkout/route.ts`'s hosted Stripe Checkout Session, `app/api/webhooks/stripe/route.ts`) and found it genuinely real and working, but entirely Stripe-shaped end to end: `Payment.stripePaymentIntentId`/`stripeFee` as literal columns, a 4-value `PaymentStatus` enum (PENDING/SUCCEEDED/FAILED/REFUNDED) with no room for authorization, partial refunds, disputes, or ACH's pending/processing/returned states, and a webhook handler that silently ignored `charge.refunded`, `charge.dispute.created`, and `payment_intent.canceled` — a real refund or dispute from the Stripe dashboard left `Payment.status` permanently stuck at `SUCCEEDED`. Separately confirmed the admin invoice module's `InvoicePayment` model is a fully independent, manually-entered payment record (any method, no processor integration) — not in scope for this abstraction and never to be confused with the storefront `Order`/`Payment` path.

Added (all additive): `PaymentProvider` enum (`STRIPE`, plus unused `GOCARDLESS`/`PAYPAL` reserved for the Phase 2/3 evaluations), `StorefrontPaymentMethodType` enum (`CARD`/`ACH`/`APPLE_PAY`/`GOOGLE_PAY`/`CASH_APP`/`PAYPAL`/`VENMO`), six new `PaymentStatus` values (`PROCESSING`, `AUTHORIZED`, `PARTIALLY_REFUNDED`, `RETURNED`, `CANCELLED`, `DISPUTED`), and new `Payment` columns (`provider`, `methodType`, `providerTransactionId` — a generic unique field mirroring `stripePaymentIntentId`'s value for today's Stripe rows, meant for a future provider's own transaction id — `processorFeePercent`, `processorFeeFixed`, `refundedAmount`, `settledAt`, `payoutId`, `disputedAt`, `completedAt`). `stripePaymentIntentId`/`stripeFee` are untouched, still what the webhook's idempotency check and `lib/export.ts`'s CSV export key off of.

The abstraction itself (`lib/payments/types.ts`'s `PaymentProviderAdapter`/`NormalizedPaymentEvent`, `lib/payments/providers/stripe.ts`'s `normalizeStripeEvent`, `lib/payments/reconcile.ts`'s `reconcilePaymentEvent`) directly mirrors the `ShippingProvider` precedent (Decision 22): one small interface, one real adapter today, a second provider is a new file implementing the same interface rather than new branches scattered through checkout/webhook code. The Stripe webhook route now calls `normalizeStripeEvent`/`reconcilePaymentEvent` for the three previously-unhandled event types, while `checkout.session.completed`'s existing bespoke logic (creates the `Payment` row for the first time, issues the invoice, logs expenses, sends the confirmation email) stays exactly as it was — a generic reconciler shouldn't own first-time row creation, only state transitions on a payment that already exists.

**Reason**: Requested as Phase 1 of a larger owner-specified payment migration (ACH/Pay-by-Bank as the preferred method, multi-wallet checkout, saved payment methods, admin payment settings, real processing-cost tracking) that explicitly calls for the underlying Order/Invoice/Customer/Inventory/Fulfillment systems to stay independent of any one payment company, and for existing Stripe behavior to move behind the abstraction in this exact phase before any new provider or checkout UI work begins.

**Alternatives considered**: Renaming `stripePaymentIntentId` to a generic column instead of adding `providerTransactionId` alongside it (rejected — touches the webhook's own idempotency lookup and every existing row's authoritative key for zero present benefit; the additive field gets the same future-proofing without that risk). Making the reconciler also handle `checkout.session.completed` (rejected — that event does meaningfully more than a status transition, and folding row-creation into a "just apply this status" helper would make the generic path stop being generic). Waiting to build the abstraction until a second provider (ACH) actually exists (rejected — the owner's own phased spec calls for the abstraction first specifically so ACH doesn't get bolted on as Stripe-shaped code that needs a second rewrite).

**Benefits**: Verified end-to-end against a genuinely computed Stripe webhook test signature (`Stripe.webhooks.generateTestHeaderString`), not a mocked auth check — a disposable rehearsal script drove a seeded `Payment` through a partial refund (direct reconciler call), a full refund and a dispute (both through the actual exported route handler), confirmed a full refund moves `Order.status` to `REFUNDED` while a partial refund or dispute deliberately does not, confirmed an invalid signature is still rejected, and confirmed an event referencing an unknown payment intent is a safe no-op. `normalizeStripeEvent` is also independently unit-tested (10 cases, no DB/network) since it's a pure function.

**Drawbacks**: Whether a dispute should freeze fulfillment, and whether a partially-refunded order needs its own `OrderStatus` value, are real business decisions this PR deliberately did not make — `Payment.status` reflects the true provider-side state, but `Order.status` only moves for the two events that already had a matching enum value (full refund, cancellation). `PROCESSING`/`AUTHORIZED`/`RETURNED` exist on `PaymentStatus` now but are unused until the ACH work (task #169) actually writes them — reserved capacity, not dead code by accident.

## 29. Storefront Orders get real inventory reservation, as a separate `OrderReservation` model rather than widening the existing invoice-scoped one

**Decision**: Auditing for the ACH work (task #169 — "reserve inventory while payment is processing") surfaced a real, pre-existing gap: `app/api/checkout/route.ts` and `app/api/webhooks/stripe/route.ts` never reserved or deducted `Product` stock for a storefront `Order` at all, regardless of payment method — only an availability check at checkout-creation time, nothing after. Two concurrent checkouts for the last unit of a product could both succeed today. Fixed by adding a new `OrderReservation` model (`lib/inventory/orderReservations.ts`) that mirrors `InventoryReservation`'s proven shape and discipline — Tx-core-plus-public-wrapper functions, idempotent by status transition (ACTIVE → FULFILLED or ACTIVE → RELEASED, a second call against a non-ACTIVE row is always a safe no-op), shortfall-aware reservation math — but points at `Order`/`OrderItem` instead of `Invoice`/`InvoiceItem`, and is deliberately smaller (no admin correction panel, no quantity-adjust-in-place, no restore/reverse-fulfillment actions, since storefront Orders don't have those workflows). Both models share the same underlying stock-accounting primitives (`computeInventoryStatus()`, `Product.reservedUnits`, the `ReservationStatus` enum) and now both write to the same `InventoryLedgerEntry` audit table (given new nullable `orderId`/`orderItemId` columns alongside the existing `invoiceId`/`invoiceItemId`).

Checkout now reserves every line item inside the same transaction as `Order` creation — a shortfall on any *non-backordered* item (a real race: someone else bought the remaining stock) rolls the whole order back before ever calling Stripe, returned to the customer as a clear error. A shortfall on a `backorderEnabled` product is expected (physical stock is already zero by definition) and never blocks checkout — that's the entire point of backorder support. If Stripe session creation itself then fails, the just-committed reservations are released and the order marked `CANCELLED` in a dedicated catch block, so a Stripe-side error never leaves stock silently held against an order that will never be payable. The webhook's existing card-success path now fulfills (deducts) the reservation in the same handler that already marks the order `PAID`; the existing `payment_intent.payment_failed` path now releases it.

**Reason**: Requested implicitly by the ACH spec's own lifecycle requirement, but genuinely necessary for the card flow too — this was scoped as its own prerequisite PR (task #174) rather than folded into the ACH PR, so it could be verified independently before ACH's async processing/authorization complexity builds on top of it.

**Alternatives considered**: Making `InventoryReservation.invoiceId`/`invoiceItemId` optional and adding parallel `orderId`/`orderItemId` columns to reuse one model (rejected — that model and its full correction/adjustment/restore surface is mature and actively used in production by the admin invoice module for real backorder workflows; widening its required-field contract risks a working system for a currently-inactive storefront feature, for a case that doesn't need most of that surface anyway). Reserving stock only for ACH orders, leaving card orders as they were (rejected — inconsistent, and leaves the actual concurrent-checkout race in place for the payment method that will presumably see the most volume).

**Benefits**: Verified against real Prisma state and the actual checkout/webhook route handlers (not mocked) — a disposable rehearsal test drove a real Stripe test-mode Checkout Session through: reserving 2 of 3 units, rejecting a second checkout that would exceed the remaining 1 unit (confirming the transaction rolls back cleanly, no orphaned `Order` or phantom `reservedUnits`), fulfilling via a genuinely-signed `checkout.session.completed` webhook event (confirming `physicalStockOnHand` actually drops and the reservation moves to `FULFILLED`), and releasing via a genuinely-signed `payment_intent.payment_failed` event (confirming stock returns to available and the order is `CANCELLED`).

**Drawbacks**: The Clerk `auth()` call in `app/api/checkout/route.ts` pulls in the `server-only` package, which throws when the route handler is imported outside a real Next.js request context — the rehearsal test had to be written as a mocked-Clerk vitest test rather than a plain `tsx` script (every other rehearsal script this session used) to work around it. No functional impact, just a testing-mechanics note for whoever writes the next one.

## 30. ACH / Pay by Bank (Phase 2) — a genuinely async payment lifecycle, one shared "mark paid" tail for card and ACH, mandate evidence kept structurally separate from raw bank data (which never exists in this database)

**Decision**: Added `'us_bank_account'` alongside `'card'` in `app/api/checkout/route.ts`'s Stripe Checkout Session `payment_method_types` — Stripe's own hosted Checkout page collects and verifies the bank account (Financial Connections or manual micro-deposits) and handles ACH mandate collection itself; this codebase never receives, transmits, or stores a raw account/routing number, online-banking credential, or Financial Connections token. What it does receive back from Stripe (bank name, last 4, account type, a `PaymentMethod` id, a mandate id) lands in new, purely-additive `Payment` columns (`bankName`, `bankAccountLast4`, `bankAccountType`) and a new `AchAuthorization` model (`stripePaymentMethodId`, `mandateId`, `authorizationVersion`, `authorizedAt`, `ipAddress`/`userAgent`, `revokedAt`/`revokedBy` — evidence a specific debit was actually authorized, never overwritten, per the owner spec's "do not initiate an ACH debit without the required authorization").

The core problem this PR actually solves: ACH doesn't settle synchronously the way a card does. Stripe's documented pattern for this is that `checkout.session.completed` fires once the customer submits their bank details (session `payment_status: 'unpaid'` for an async method), while the *authoritative* success/failure signal arrives later via dedicated `checkout.session.async_payment_succeeded`/`checkout.session.async_payment_failed` events — sometimes days later, once the bank debit actually clears or bounces. `lib/payments/providers/stripe.ts`'s `normalizeStripeEvent` now branches `checkout.session.completed` on `payment_status` (`'paid'` → `SUCCEEDED`/`CARD`, anything else → `PROCESSING`/`ACH`) and adds cases for both new async events. The webhook route mirrors that: a `paid` session goes straight to the existing "mark paid" path; an `unpaid` (ACH) session creates a `PROCESSING` `Payment` row, captures mandate/bank evidence via a best-effort `stripe.paymentIntents.retrieve` call, and — critically — leaves the `OrderReservation` from task #174 `ACTIVE` and `Order.status` at `PENDING`, never `PAID`. Only `checkout.session.async_payment_succeeded` actually fulfills the reservation and marks the order paid.

New `lib/payments/orderFulfillment.ts` extracts that "mark paid" tail (fulfill reservations, upsert `Payment` to `SUCCEEDED`, issue the invoice, log expenses, send the order-confirmation email) into one function, `markOrderPaid()`, called by BOTH the synchronous card path and the asynchronous ACH success path — "what happens when an order gets paid" is defined in exactly one place regardless of which payment method got there. A separate `estimateAchFee()` (`lib/stripe.ts`, Stripe's published 0.8%-capped-at-$5 ACH pricing) is used instead of `estimateStripeFee()`'s card-shaped 2.9%+$0.30 when `methodType` is `ACH`. A new customer-facing `ACH_PAYMENT_PROCESSING` email (`emails/AchPaymentProcessing.tsx`) is sent when the debit is submitted — deliberately never using the words "confirmed" or "paid," since that's what the real `ORDER_CONFIRMATION` email (unchanged) is for once `async_payment_succeeded` actually fires.

**Reason**: Requested directly as Phase 2 of the payment migration, with an explicit lifecycle spec (create the transaction → submit the debit → mark Processing, not Paid → hold reservation → wait for authoritative confirmation → success marks paid / failure releases and notifies) and an explicit security boundary (no raw bank credentials in Pepscore Lab's own database, ever).

**Alternatives considered**: Treating `checkout.session.completed` as sufficient signal for ACH the same way it already is for cards (rejected — this is precisely the mistake Stripe's own docs warn against for async payment methods; it would mark an order paid, ship-eligible, and email a confirmation for a bank debit that hasn't actually cleared and might still bounce). Storing the mandate id directly on `Payment` instead of a separate `AchAuthorization` model (rejected — the owner spec asks for a specific evidence shape, including a revocation state a completed-payment row has no natural home for, and a dedicated model makes "was this debit actually authorized" independently auditable rather than one field among many on the payment record). Retrieving ACH bank/mandate details synchronously as part of the main webhook flow with no fallback (rejected — `fetchAchDetails` is explicitly best-effort/never-throws, since a transient Stripe API failure fetching *display* metadata should never block recording that a payment attempt exists).

**Benefits**: Verified against real Prisma state and the actual webhook route handler with genuinely-signed Stripe events (not mocks) covering the full lifecycle: an unpaid `checkout.session.completed` holds the reservation and creates a `PROCESSING` payment (confirmed idempotent on redelivery — no duplicate row), a direct `markOrderPaymentProcessing()` call with explicit bank/mandate input verifies the `AchAuthorization` capture path, a genuinely-signed `checkout.session.async_payment_succeeded` fulfills the reservation and deducts real stock exactly like the card path already does, and a genuinely-signed `checkout.session.async_payment_failed` releases the reservation and cancels the order. `AdminOrdersTable`/`app/api/admin/orders/route.ts` now surface payment provider/method/status per order so an admin can actually see which orders are ACH-processing versus paid.

**Drawbacks / explicit scope boundary**: There is currently no Customer Portal view of storefront `Order`s at all (confirmed by audit — the portal is built entirely around the `Invoice` model) — full customer-facing ACH status visibility stays out of scope for this PR rather than being rushed in as a disconnected feature; it belongs with task #172's Customer Portal payment-method work. `fetchAchDetails`'s mandate-id lookup couldn't be exercised against a real completed Stripe Checkout Session in this environment (that requires actually completing Stripe's hosted bank-linking flow, not automatable from a script) — verified instead via a direct call to the capture function with explicit input, and via the fee/status/reservation state machine end-to-end through the real route. `RETURNED` exists on `PaymentStatus` and is handled by `markOrderPaymentFailedOrReturned()`'s signature but nothing currently sets it specifically (Stripe's `async_payment_failed` doesn't distinguish an outright failure from a later bank return) — reserved for when that distinction becomes available or needed.

## 31. Admin Payment Settings — real checkout-method gates kept structurally separate from readiness-only display flags; processing-cost analytics computed live from `Payment` rows, never fabricated

**Decision**: New `PaymentSettings` singleton (`lib/payments/settings.ts`, same fixed-id upsert pattern as `InvoiceSettings`) with 7 boolean toggles, but they are NOT all the same kind of thing, and the code says so explicitly rather than pretending otherwise: `cardEnabled`/`achEnabled`/`cashAppEnabled` are real gates — `app/api/checkout/route.ts` now builds Stripe Checkout's `payment_method_types` array from them at request time instead of the hardcoded `['card', 'us_bank_account']` PR #115 shipped. `applePayEnabled`/`googlePayEnabled` are deliberately informational-only: Stripe's hosted Checkout has no separate parameter for either — they ride on `'card'` automatically whenever the visitor's browser/device supports them — so these two exist purely so the settings page can show accurate readiness status without a future maintainer mistaking them for something `checkout.sessions.create` actually reads. `paypalEnabled`/`venmoEnabled` are pure readiness flags: no PayPal/Venmo integration exists yet (task #170), so there's nothing for them to gate. `updatePaymentSettings()` refuses to save a state where `cardEnabled`/`achEnabled`/`cashAppEnabled` are all false, so an admin can never accidentally leave checkout (if it were ever turned on) with zero offerable payment methods.

New `lib/payments/analytics.ts`'s `getPaymentCostAnalytics()` is a real `prisma.payment.groupBy()` aggregation (by `methodType`/`provider`, filtered to `SUCCEEDED`/`PARTIALLY_REFUNDED`/`REFUNDED` — a `PROCESSING`/`FAILED`/`CANCELLED` row never actually incurred a fee, so including it would overstate cost) — never a mocked or hand-typed number. The ACH-vs-card savings comparison applies the exact same fee formulas `lib/stripe.ts`'s `estimateStripeFee`/`estimateAchFee` use (now exported as named constants — `STRIPE_CARD_FEE_PERCENT`/`STRIPE_CARD_FEE_FIXED`/`STRIPE_ACH_FEE_PERCENT`/`STRIPE_ACH_FEE_CAP` — specifically so this file can't drift from a second hardcoded copy) to a real ACH volume's total dollars and transaction count, computing what that same volume would have cost as card (`amount * cardPercent + count * cardFixed`, the fixed fee correctly multiplied per-transaction rather than applied once to the aggregate sum) rather than a rough blended-rate estimate.

**Reason**: Requested directly as the Admin Payment Settings + processing-cost analytics roadmap item, with an explicit requirement not to expose secrets in the browser (the settings page shows only booleans — "Stripe Configured," "Test Mode," "Checkout Enabled" — derived server-side from whether `STRIPE_SECRET_KEY` is present and starts with `sk_test_`, never the key itself) and to compute real internal cost data rather than placeholder numbers.

**Alternatives considered**: A single flat `enabledMethods: string[]` field instead of 7 named booleans (rejected — loses the type safety and self-documentation of each method having its own column, and makes the real-gate-vs-readiness-only distinction harder to express and enforce in code). Estimating ACH savings with a blended average fee rate applied to total ACH volume instead of the per-transaction formula (rejected — undercounts the card-equivalent fixed-fee component for a volume made of many small transactions, since $0.30-per-transaction doesn't scale the same way a percentage does).

**Benefits**: Verified against real Prisma state: `updatePaymentSettings()`'s at-least-one-enabled guard actually rejects an all-off write (not just documented as a rule), disabling ACH and leaving card on actually changes what the real Stripe test-mode Checkout Session the route creates offers (confirmed by retrieving that exact session back from Stripe's API and asserting `payment_method_types` — not inferred from the request code, the literal response Stripe gave back), and the analytics math was checked against hand-computed expected values from seeded `Payment` rows with known amounts/fees.

**Drawbacks**: The settings page's checkout-method toggles autosave on click (no separate "Save" step) — consistent with several other single-purpose admin toggles in this codebase, but means there's no draft/cancel state if an admin changes their mind mid-click; matches the existing UX pattern (`InvoiceEmailSettingsForm`, etc.) rather than introducing a new one. Cash App Pay (`cashAppEnabled`) can be toggled on today and will genuinely change what Stripe Checkout offers, but hasn't been exercised end-to-end the way card/ACH were in PRs #114/#115 — it defaults off specifically because it's real-but-unverified capability, not because it doesn't work.

## 32. Checkout moved from a hosted-page redirect to Stripe's embedded Checkout; PayPal wired as a real (owner-gated) fourth method, Venmo confirmed to have no Stripe path at all

**Decision**: `app/api/checkout/route.ts` now creates the Stripe Checkout Session with `ui_mode: 'embedded'` instead of the default hosted mode, returning `session.client_secret` (a new `{ clientSecret }` response shape, replacing `{ url }`) instead of a redirect URL. `components/storefront/CheckoutForm.tsx` mounts `@stripe/react-stripe-js`'s `EmbeddedCheckoutProvider`/`EmbeddedCheckout` in-page once that secret comes back, rather than navigating the whole browser tab away to a Stripe-hosted URL. `@stripe/stripe-js` (already an installed but *entirely unused* dependency — confirmed via a repo-wide grep before touching it) was upgraded from v4 to v9 to satisfy `@stripe/react-stripe-js`'s peer requirement; safe specifically because nothing in the codebase called any of its APIs yet, so there was no existing call site to break. `app/checkout/success/page.tsx` now reads the real `Order.status` instead of unconditionally declaring "Order Confirmed" — an ACH order arriving on this page is very likely still `PENDING` (payment submitted, not yet cleared), and the page now shows a distinct "Payment Processing" state with honest copy instead of claiming a debit that hasn't settled has been confirmed.

Also wired `PayPal` as a genuine fourth Stripe Checkout payment method type (`paypalEnabled` in `PaymentSettings`, confirmed as a real, valid `Stripe.Checkout.SessionCreateParams.PaymentMethodType` against the installed SDK's own type definitions, not assumed) — `paypalEnabled` was previously documented as "readiness only" in PR #116 before this PR actually wired it into `payment_method_types`. It only actually works once PayPal itself is turned on for this Stripe account in the Stripe Dashboard (Settings > Payment methods) — an account-level, owner-gated prerequisite Stripe itself enforces; if it isn't enabled, Stripe rejects session creation and the existing Stripe-error catch path (release the reservation, surface the error) handles it exactly like any other Stripe API failure, so there's no way to end up in a broken or ambiguous state by turning this toggle on before the account is ready. Venmo (`venmoEnabled`) was confirmed to have **no Stripe Checkout payment method type at all** (checked against the same SDK type definitions) — it's a PayPal-owned product only reachable through PayPal's own separate merchant checkout integration, not something Stripe proxies. `venmoEnabled` stays a permanent readiness-only flag; the settings page now says exactly why, rather than implying it's merely unbuilt-but-possible the same way Apple Pay/Google Pay are.

**Reason**: Requested directly — a modern in-page checkout experience (not a full-page bounce to Stripe) supporting card/ACH/Cash App Pay/PayPal where technically eligible, plus an honest evaluation of whether PayPal and Venmo are actually available through the current architecture before building anything speculative.

**Alternatives considered**: Building a raw Stripe Payment Element with a hand-authored payment method list/ordering (e.g., to visually promote "Pay by Bank — Recommended" as the first, distinctly-labeled option) instead of Embedded Checkout (rejected for now — Embedded Checkout reuses 100% of the existing Checkout Session-based backend from PRs #113-116 unchanged, while a raw Payment Element would require re-implementing ACH mandate collection, Financial Connections bank linking, and payment-method-specific UI by hand; Stripe's own embedded UI doesn't expose a "reorder/relabel this specific method as recommended" API, so that exact visual treatment isn't achievable with either approach without significantly more custom UI work — flagged here honestly rather than claimed as done). Treating every arrival on `/checkout/success` as "confirmed" regardless of payment method (rejected — see the ACH entry, PR #115; this was the same category of mistake, now actually fixed at the point a customer would see it).

**Benefits**: Verified against real Prisma state and a genuine Stripe test-mode API call (not a mock): a disposable rehearsal test drove the actual checkout route, retrieved the resulting session back from Stripe's own API, and confirmed `session.ui_mode === 'embedded'`, `session.client_secret` matches what the route returned to the client, and `session.url` is `null` (proof this is genuinely embedded, not hosted). `npx tsc`/`eslint`/`vitest`/`next build` all clean.

**Drawbacks**: No real browser can complete an embedded Stripe Elements checkout end-to-end in this environment (that requires a live page load and real user interaction inside Stripe's iframe, not something a script can drive) — verified instead via the session-creation contract (client_secret, ui_mode, payment_method_types) exactly as far as this environment allows, matching the same honest limitation flagged for ACH's mandate-detail lookup in PR #115. The "Pay by Bank — Recommended" *visual promotion* (a distinctly labeled, first-position badge) is not achievable with Embedded Checkout as built here — Stripe's own embedded UI controls its own method ordering/presentation; a raw Payment Element rebuild would be required for that specific treatment, and is not part of this PR.

## 33. Saved payment methods reuse the embedded-Checkout mechanism itself (mode: 'setup' instead of 'payment') rather than a second UI pattern; a returning customer's saved methods surface via Stripe's own `customer` param, no custom picker built

**Decision**: New `Customer.stripeCustomerId` (nullable, created lazily — confirmed via audit that no Stripe Customer object existed anywhere in this codebase before this PR, since checkout has always been guest/email-based) and `SavedPaymentMethod` (Stripe PaymentMethod id + safe display metadata only — brand/last4/expiry for a card, bank name/last4/account type for ACH, never a raw number). "Add a payment method" in the new `/account/payment-methods` portal page reuses the *exact same* `EmbeddedCheckoutProvider`/`EmbeddedCheckout` component PR #117 built for real purchases — the only difference is the Checkout Session is created with `mode: 'setup'` instead of `mode: 'payment'` (Stripe's own mechanism for collecting and verifying a reusable payment method without charging anything). One UI pattern, reused for both "pay now" and "save for later," not two independently-built ones.

For checkout itself, `app/api/checkout/route.ts` now looks up whether the authenticated, portal-linked buyer already has a `stripeCustomerId` and, if so, passes `customer: stripeCustomerId` to the Checkout Session instead of `customer_email` (the two are mutually exclusive on Stripe's own API). Stripe's embedded Checkout then surfaces that customer's saved methods automatically — no custom "choose a saved card" picker was built, because Stripe's own UI already does this once a real `customer` id is attached. Checkout itself never creates a Stripe Customer — that only happens the first time someone explicitly adds a method in the portal — so a guest or a linked customer who's never saved anything checks out exactly as before.

**Reason**: Requested directly — card and bank account, add/remove/set-default/select-at-checkout, provider tokenization only, no raw credentials ever stored.

**Alternatives considered**: A raw `SetupIntent` + hand-built Stripe Elements form for "add a method" (rejected — Embedded Checkout in `mode: 'setup'` is Stripe's own recommended mechanism for exactly this, and reusing the same component already proven in PR #117 means there's no second integration surface to trust or maintain). Building a custom "select a saved method" UI at checkout instead of attaching `customer` to the session (rejected — Stripe's embedded Checkout already does this correctly once a real Customer id is present; a hand-built picker would just be a second, weaker implementation of something Stripe already provides for free).

**Benefits**: Verified against real Prisma state and real Stripe test-mode API calls — not mocks: `getOrCreateStripeCustomer()` creates a genuine Stripe Customer (confirmed via `stripe.customers.retrieve()`) and is idempotent on a second call (same id returned, no duplicate); `createAddPaymentMethodSession()` produces a real embedded `mode: 'setup'` Checkout Session with a genuine `client_secret`; list/set-default/remove were exercised against a real PaymentMethod object created and attached via Stripe's own documented test token (`tok_visa`) rather than a fabricated id, including confirming `removeSavedPaymentMethod()` actually calls `stripe.paymentMethods.detach()` (verified by retrieving the PaymentMethod back from Stripe afterward and confirming `customer` is now `null`, not just checking the local DB row). An ownership-check regression guard already present in this codebase (`app/api/account/portalAuthCoverage.test.ts`) caught that the new `[id]` route needed an explicit `customerId: customer.id` lookup at the route level, not just inside the service function — fixed to match every other `app/api/account/[id]/**` route's existing defense-in-depth convention.

**Drawbacks**: `capturePaymentMethodFromSession()` (the function that runs when a customer returns from a *completed* setup Checkout Session) could not be exercised end-to-end in this environment for the same reason as PR #117's checkout session and PR #115's ACH mandate lookup — completing Stripe's hosted/embedded UI requires real browser interaction. Verified instead via the DB-persistence and Stripe-API-call logic directly, using a real attached PaymentMethod created through Stripe's own test-token API rather than through the actual embedded form. The Apple Pay/Google Pay/Cash App Pay/PayPal methods enabled in `PaymentSettings` are not yet save-able as reusable methods — only card and ACH are wired into the setup-session `payment_method_types` here, matching what the roadmap item asked for explicitly.

## 34. Payment-change safety, scoped to the one real gap an audit actually found: a DRAFT invoice can drift out of sync with an already-open embedded Checkout Session

**Decision**: Audited before writing any code (per the task's own instruction not to manufacture scope). Grepped every `prisma.order.update`/`prisma.orderItem.update` call site in the codebase: a storefront `Order`'s `total`/line items are fixed at checkout-creation time and nothing mutates them afterward — admin order updates only ever touch `status`/`notes`, shipping-label purchase only touches `shippingCost`/`fulfillmentStatus` *after* the Fulfillment Gate has already required the order be paid. So the `Order` side of a Checkout Session can never go stale through any existing code path. The one real, narrow gap: `app/api/checkout/route.ts` creates the linked `Invoice` as `DRAFT` in the *same transaction* as the `Order`, before the Stripe Checkout Session is even created — meaning that invoice is a normal, editable row in the admin invoice system for the entire window a customer is filling out the embedded Checkout form. If an admin applies, adjusts, or removes a backorder compensation against that invoice during that window, its balance changes while the customer's already-open session still reflects the old, now-wrong amount — and a Checkout Session has no live-update mechanism once created.

New `lib/payments/staleSessionGuard.ts`'s `invalidateStaleCheckoutSessionForInvoice(invoiceId, reason)` is the single function this maps to: given any invoice, it no-ops immediately unless that invoice has a linked `Order` that is still `PENDING` with a live `stripeSessionId` (the ordinary admin-invoice-module case — no linked `Order` at all — is the overwhelming majority of invoices and exits on the very first check). When it does find a genuinely at-risk session, it calls `stripe.checkout.sessions.expire()` (a real, confirmed-to-exist API method) so the customer's open embedded form can no longer complete a payment for the stale amount, marks the `Order` `CANCELLED`, and releases its `OrderReservation` via the existing `releaseAllOrderReservationsTx` from task #174 — never leaving stock held against a session that can no longer be paid. Wired into the 5 real entry points in `lib/backorders.ts` that can change an invoice's balance: `applyCompensation`, `applyBackorder`, `applyDiscretionaryAccommodation`, `adjustDiscretionaryAccommodation`, `removeDiscretionaryAccommodation` — each already had a post-commit side-effect section (activity logging, customer notification) that this one more call joins, matching the existing pattern rather than inventing a new one.

**Reason**: Requested directly, with an explicit instruction to audit first and build only what the actual architecture requires rather than manufacturing scope for a task that might have little real surface area. It didn't have *no* surface area — it had exactly one genuine gap, found by tracing every place `Order`/`Invoice` totals can actually change post-session-creation.

**Alternatives considered**: A generic "any invoice update invalidates any linked order's session" hook at a lower level (e.g. inside `recalculateInvoiceFinancials` itself) — considered and rejected in favor of the 5 explicit call sites: `recalculateInvoiceFinancials` runs *inside* a Prisma transaction, and a Stripe network call must never happen inside an open DB transaction (holds a lock for the duration of an external API round-trip); the 5 public functions are exactly the set of places that already do post-commit work outside their transactions, so that's where a post-commit Stripe call belongs too. Building a full "regenerate a corrected session and live-refresh the customer's embedded iframe" flow (rejected as manufactured scope — real checkout is still OFF (`STOREFRONT_CHECKOUT_ENABLED`), there is no live customer experiencing this today, and the actually-required safety property is narrower: never let a stale amount remain payable. A "resume corrected checkout" UX is real future work once checkout is actually live and this becomes an observed operational concern, not something to speculatively build now).

**Benefits**: Verified against real Prisma state and a genuine Stripe test-mode Checkout Session — not a mock: a disposable rehearsal test drove the actual checkout route to create a real `open` embedded session, then called the real `applyDiscretionaryAccommodation()` against its linked DRAFT invoice, then retrieved that exact session back from Stripe's own API and confirmed its `status` field had genuinely transitioned from `'open'` to `'expired'` — not inferred from local DB state. Also confirmed the guard is a true no-op (no Stripe call, no side effects) for an invoice with no linked `Order` at all, the ordinary case for every admin-created invoice in the system.

**Drawbacks**: `applyCompensation` in particular is called from multiple places (`applyBackorder`, potentially direct admin actions) — every one of them now pays the cost of one extra `prisma.invoice.findUnique` per call, even though it resolves to a no-op for the vast majority of invoices (anything not linked to a still-PENDING storefront Order). Accepted as a negligible, correctly-scoped cost given what it prevents. This safety net only covers the backorder-compensation family of balance changes — if a future feature introduces a different way to change a DRAFT invoice's total pre-payment, that new code path would need its own call to `invalidateStaleCheckoutSessionForInvoice`, the same way each of these 5 did; it is not automatically covered by some lower-level hook.

## 35. Portal invitation eligibility excludes bare leads — a Customer needs at least one real invoice before a portal account makes sense

**Decision**: `lib/portal/rolloutAudience.ts`'s `computeEligibleInviteAudience()` gained a new exclusion category, `leadStageFlagged`, alongside the existing `duplicateFlagged`/`testDataFlagged`: any unclaimed customer whose `status` is still `LEAD`, `INTAKE_SENT`, or `INTAKE_COMPLETED` — i.e. `computeCustomerStatus()` (`lib/customers/status.ts`) has never found a real invoice for them — is excluded from `eligible` the same conservative way duplicates and test data are: surfaced in the admin report, never silently invited. `isLeadStage()` is the pure, exported predicate.

**Reason**: Audited before assuming the existing eligibility rule needed anything, per the task's own instruction not to invent a requirement if current behavior was already correct. It wasn't: a live, read-only check against production found 6 of 17 real `Customer` rows were `LEAD` status (no invoice ever issued), and 4 of those were sitting inside the then-"14 eligible" bulk-invite audience. A portal account exists to show a customer their own invoices/orders/tracking — inviting someone with literally nothing to view there is exactly the "do not assume every raw lead should automatically receive portal credentials" failure mode called out when this automation was specified.

**Alternatives considered**: Filtering by `CustomerStatus` directly in the base `prisma.customer.findMany` query (deny-list the three lead-stage statuses inline) — rejected in favor of a separate, reported exclusion bucket: silently narrowing the base query would make a lead-stage customer indistinguishable from one excluded for a different reason (duplicate, test data, conflict), and the whole point of every other exclusion category here is that an admin can see *why* someone isn't in the audience, not just that they aren't. A stored "portal-eligible" boolean on `Customer` — rejected the same way every other derived-vs-stored decision in this module has been: `CustomerStatus` is already recomputed live from real invoice state at every relevant write, so re-deriving lead-stage from it can never drift out of sync the way a second stored flag could.

**Benefits**: Verified against the real, current production `Customer` table (not synthetic data) before writing any code, so the fix targets an actually-observed gap rather than a hypothetical one. `isLeadStage()` and the two other pure exclusion predicates it sits alongside (`classifyByContactInfo`, `findDuplicateContactCustomerIds`) are all independently unit-tested.

**Drawbacks**: `CustomerStatus`'s `LEAD`/`INTAKE_SENT`/`INTAKE_COMPLETED` boundary is itself a judgment call about "when does a lead become a real customer" — a business could reasonably want to invite an `INTAKE_COMPLETED` customer (they've filled out real intake information, just haven't been invoiced yet) before their first invoice exists. That boundary was drawn at "has at least one invoice" as the safest, least-surprising authoritative point rather than the most generous one; moving it earlier is a product decision for the owner to make explicitly, not something to guess at here. **Superseded by Decision #36** — the owner made exactly that call.

## 36. Portal eligibility's "no invoice yet" exclusion (#35) is overridden by an explicit admin `leadStatus: CONVERTED` marking

**Decision**: `isLeadStage()` now returns `false` immediately whenever `Customer.leadStatus === 'CONVERTED'`, regardless of `status`/invoice history — a zero-invoice customer an admin has explicitly marked Converted is treated as a genuine customer for portal-invite purposes, not excluded as a bare lead.

**Reason**: Directly challenged: Decision #35's "has at least one invoice" rule would incorrectly exclude a real customer in scenarios with no invoice yet but real intent — an admin arranging an in-person sale, entering a customer ahead of their first invoice, or a future storefront/account flow that creates a Customer before an Order completes. Auditing the schema for an existing authoritative signal (rather than inventing a new stored field) found `Customer.leadStatus` — a separate CRM triage enum (`NEW/CONTACTED/QUALIFIED/CONVERTED/CLOSED`) already documented in its own schema comment as "never auto-computed, only ever changed by an explicit admin action," completely independent of the invoice-derived `status` field. That is exactly the "admin vouches for this person" signal #35's own Drawbacks section said would need an explicit product decision.

**Alternatives considered**: A new dedicated `portalEligible` boolean or enum on `Customer` — rejected because `leadStatus` already encodes this distinction and adding a second, parallel field risks the two silently disagreeing (a customer marked `CONVERTED` in the CRM sense but `portalEligible: false` by omission, or vice versa) for no real benefit over reusing the one that already exists. Removing the invoice-count check entirely (treat every non-excluded customer as eligible) — rejected: it would have re-admitted the same real bare-lead records (individually audited, see Benefits below) that #35 was built to catch, since none of them carry any signal of being real customers beyond existing as a `Customer` row.

**Benefits**: The 4 real customers #35 excluded were individually audited by name before this fix, not assumed — each has exactly one admin-generated intake link that was viewed but never submitted, no invoice, no lead capture, and (crucially) `leadStatus: NEW` in every case, meaning none of them were an admin's confirmed sale. The fix therefore changes zero real outcomes today (eligible count stays 10) while making the *rule* correct for the case #35 could get wrong — verified with a disposable rehearsal test creating a zero-invoice `leadStatus: CONVERTED` customer and confirming they land in `eligible`/`ELIGIBLE`, not `leadStageFlagged`/`NOT_ELIGIBLE`.

**Drawbacks**: This still requires an admin to remember to mark a customer Converted before their first invoice if early portal access is wanted — there's no automatic signal for "this is definitely a real sale in progress" short of an actual invoice or an explicit CRM triage action. Accepted as correct: guessing at intent from anything weaker (a phone number present, an intake link viewed, a note field) would reintroduce exactly the "invite a real lead automatically" risk #35 was written to prevent.

## 37. The automated rollout cron moved from a one-time frozen-snapshot batch to live, ongoing eligibility

**Decision**: `app/api/cron/portal-invite-rollout/route.ts` now calls `computeEligibleInviteAudience()` fresh on every invocation and invites everyone it returns (subject to the existing kill-switch/dry-run/allowlist/cap gates), rather than intersecting the live-eligible set against `PortalRolloutSettings.audienceSnapshot` — the list of ids captured once, at the moment an admin clicked Activate. `audienceSnapshot` is still written by `activatePortalRollout()` and still shown in the admin UI, but purely as a historical record ("this many customers were eligible when this was turned on"), never read anywhere as a filter. `lib/portal/rollout.ts`'s now-unused `getAudienceSnapshotIds()` was deleted rather than left as dead code.

**Reason**: Explicit, direct owner instruction: `PortalRolloutSettings.activatedAt` should represent "the owner has approved automated invites are running," an ongoing state, not a one-time batch approval — and the Customer Portal Adoption Automation spec's core requirement is that a customer created *after* the original rollout still gets onboarded automatically, without the owner having to remember to re-activate. The previous design (built in direct response to a real incident — see the rollout-safety work's own history) intentionally scoped every send to exactly what a human had reviewed at approval time; that was the right call for a one-time bulk-invite decision, but is the wrong call for a feature whose entire point is "the owner should not have to manually track who still needs an invitation."

**Alternatives considered**: A second, separate scheduled reconciliation cron with its own independent activation gate layered on top of the existing one-time rollout — considered and rejected as needless duplication: it would mean two `PortalRolloutSettings`-shaped activation records, two "is this really live" questions for an owner to track, and two nearly-identical cron routes to keep in sync, when the actual fix is one field (`audienceSnapshot`) no longer being read as a filter. Re-snapshotting on every cron run (refresh the stored list each invocation instead of removing the filter) — rejected as pointless: a snapshot that gets silently overwritten every few minutes provides none of the original safety property (a human genuinely reviewed this exact list) while adding a write nobody reads back for filtering.

**Benefits**: Every other safety gate — `CUSTOMER_AUTO_INVITES_ENABLED`, the kill switch, dry-run (defaults on), the allowlist, the per-run cap, `pausedAt` — is completely unaffected and still independently sufficient to stop a real send; this change only touches *which* eligible customers a live run considers, never *whether* or *how many* it's allowed to actually contact. `generatePortalInvite()`'s own idempotency guards (reuse an existing active invite, refuse an already-linked customer) were already the real duplicate-send protection, not the snapshot — so removing the snapshot filter doesn't weaken duplicate protection at all. `lib/portal/adoptionStatus.ts`'s `INVITE_PENDING` status (added in the same work session) now means what its own name says — "eligible and automation is live" — instead of also silently requiring snapshot membership, a distinction that would have confused an owner looking at the dashboard.

**Drawbacks**: The two-step Activate confirmation copy had to be rewritten so an admin activating today understands they're agreeing to an ongoing process, not a fixed one-time batch — reviewed and updated in `components/admin/PortalRolloutPanel.tsx` as part of this same change, since the old copy ("approve as an immutable snapshot... never anyone who qualifies later") would now be actively wrong. An admin who wants a genuine one-time-only batch send (approve exactly today's list, then require a fresh explicit decision before contacting anyone else) no longer has that as a built-in mode — Pause is the closest equivalent (stops all sends without losing the activation record) but doesn't distinguish "stop because I want to review the next batch" from "stop for an unrelated reason."

## 38. No separate real-time event trigger was built for "a new customer just became portal-eligible" — the existing daily cron plus the existing manual invite button already satisfy it

**Decision**: `lib/customers.ts`'s `createCustomer()` gained no new invite-triggering code, and no webhook/event hook was added anywhere else in the customer-creation path. Two things already in place cover the "the owner should not have to remember which new customers still need portal access" requirement: (1) `vercel.json`'s `portal-invite-rollout` cron runs daily (`0 15 * * *`) and, since Decision #37, recomputes live eligibility on every run — so any customer who becomes eligible today is auto-invited within 24 hours with zero admin action; (2) `PortalAccessSection.tsx`'s existing "Invite to Portal" button already gives an admin an immediate, one-click way to invite a specific customer the moment they create or convert one, if 24 hours isn't acceptable for that case.

**Reason**: The Customer Portal Adoption Automation spec asked for "event-driven eligibility triggers where practical" plus "a recurring scheduled audit as a self-healing backstop," explicitly preferring that combination over a pure poll. Before building a new trigger, audited what already existed (per the task's own instruction to implement only the real gap): a genuine real-time trigger would mean either a synchronous Prisma middleware/transaction hook on every `Customer` write (risking a slow or failing invite-send blocking an otherwise-unrelated admin action, like editing a customer's notes) or a queued background job (new infrastructure — Pepscore has no job queue today). Weighed against a once-daily cron with same-day-if-urgent manual override, the added complexity wasn't justified by the actual latency need: nothing about this product requires sub-24-hour automated onboarding, and the one case that plausibly does (an admin wants to invite someone right now) already has a direct button for it.

**Alternatives considered**: A Prisma middleware hook or explicit call inside `createCustomer()` to synchronously evaluate and send an invite at creation time — rejected: a brand-new customer is created `LEAD` by default (see Decision #36) and would be excluded from eligibility on the very same request anyway, making a synchronous check a no-op in the overwhelmingly common case and pure risk (an external send, e.g. email delivery, running inside/right after the customer-creation request) in the rare one. A new lightweight event/queue table written to at every eligibility-relevant `Customer` update (status change, `leadStatus` change, portal unlink, etc.) and drained by a more-frequent cron — rejected as new infrastructure solving a latency problem nobody has reported; if a real need for faster-than-daily onboarding emerges, shortening the existing cron's schedule is a one-line `vercel.json` change, not a reason to build a second system now.

**Benefits**: Zero new code paths that could send a real invitation outside the two that already exist and are already safety-gated (the cron's full gate stack from Decision #37's header comment, and `PortalAccessSection`'s existing single-customer flow) — no new surface area to audit for the safety properties already established this session. Verified the cron's actual schedule (`vercel.json`, `0 15 * * *`) directly rather than assuming; this decision would need revisiting if that schedule were ever lengthened to, say, weekly.

**Drawbacks**: A customer converted from lead to eligible at 15:01 UTC waits up to ~24 hours for automatic invitation if nobody clicks the manual button — acceptable today given no stated urgency requirement, but worth remembering if the business later wants same-day automatic onboarding, at which point shortening the cron interval (not building new trigger infrastructure) is the first thing to try.

## 39. Invitation expiration/reissue policy — already correct, no new code needed

**Decision**: No changes. Audited the existing expiration/reissue path against the Customer Portal Adoption Automation spec's requirement for one, and confirmed it already does exactly what was asked: `computeEligibleInviteAudience()` (`lib/portal/rolloutAudience.ts`) treats a customer whose most recent invite is `INVITE_EXPIRED` or `INVITE_REVOKED` identically to one who was never invited at all — both land in the `eligible` bucket, both get picked up by the live-eligibility rollout cron (Decision #37) on its next run, and both can be manually re-invited immediately via `PortalAccessSection`'s "Invite to Portal" button. `generatePortalInvite()` (`lib/portalInvites.ts`) only ever short-circuits on an existing invite when `findActivePortalInviteFor()` finds one in the `ACTIVE` state — an expired or revoked invite doesn't satisfy that check, so a reissue creates a genuinely new row (fresh token, fresh 7-day `expiresAt`) rather than erroring or silently reusing a dead one.

**Reason**: The spec asked for an explicit expiration/reissue policy as one of the still-open Portal Adoption Automation items. Before writing anything, traced the actual behavior end to end rather than assuming a gap existed — the same "audit before building" discipline applied to the event-driven-trigger question (Decision #38) and the earlier zero-invoice eligibility fix (Decisions #35/#36).

**Alternatives considered**: None seriously — there is no code change to weigh alternatives for. The one adjacent question worth naming: whether `INVITE_EXPIRY_HOURS` (7 days) or the day-3/day-6 reminder cadence should change. Left untouched — no evidence either window is wrong, and changing them wasn't what was asked.

**Benefits**: Confirmed via direct code reading (`isLeadStage`/`getPortalInviteState`'s existing ACTIVE/CLAIMED/EXPIRED/REVOKED classification, already unit-tested in `lib/portalInviteState.test.ts`) rather than assumed from the function names. This is the same underlying behavior verified for the `TEST DeleteMe` customer in Decision-adjacent work this session: their revoked invite correctly appears with a `Revoked` date on the profile's Customer Portal section rather than blocking a future reissue.

**Drawbacks**: None identified — this decision closes an open spec item with zero code risk.

## 40. Failed-invitation handling: cron failures are now admin-visible; provider-response idempotency keys were considered and deliberately not added

**Decision**: Two real, narrowly-scoped gaps found and fixed. First, `app/api/cron/portal-invite-rollout/route.ts` previously recorded failures only in its own JSON response — never read by anyone, since a Vercel cron invocation's response body isn't surfaced anywhere — with no `AdminAuditLog` write at all (unlike the reminder cron, which already wrote one but still had no viewer). It now writes an `AdminAuditLog` row (`ROLLOUT_CRON_RUN`) every run, mirroring the reminder cron's existing `REMINDER_CRON_RUN` pattern. Second, new `lib/portal/deliveryIssues.ts` reads recent `*_CRON_RUN` audit rows and a pure `summarizeRepeatedFailures()` aggregates them by customer, and `/admin/portal-rollout` gained a "Recent Delivery Issues" card (only rendered when there's something to show) that lists recent failed runs and calls out any customer who's failed on 2+ separate runs specifically — a repeated failure is a real signal worth a look; a single transient one usually isn't.

What was **not** built: a provider-level idempotency key (e.g. Resend's `Idempotency-Key` header) to guard against double-delivery when a send's HTTP response is ambiguous (timeout, 5xx after the provider actually processed it). Audited first: no idempotency-key mechanism exists anywhere in this codebase's notification-sending layer (`lib/resend.ts`, `lib/notifications/bestEffortSms.ts`) today — the only `idempotencyKey` usages found are unrelated, in the inventory ledger. Adding one here would mean changing the shared send path every other email/SMS feature in the app also goes through, for a risk this specific to portal invites: the existing retry-safety design (`remindersSent`/`lastReminderAt` only increment on a confirmed success — see the reminder cron's own comment) already prevents the *common* failure mode (a clean provider error → safe retry next run); what it can't prevent is the *rare* one (provider silently succeeded despite an ambiguous response → a harmless duplicate reminder email, not a double-charge or any destructive action).

**Reason**: Directly asked to review failed-invitation handling and determine whether a real gap exists. It did — admin invisibility of failures — and doesn't for the idempotency-key case in a way that justifies touching shared infrastructure right now.

**Alternatives considered**: A general-purpose `AdminAuditLog` browser page — rejected as much larger scope than what was asked ("surface repeated failures," not "build an audit log viewer"); the existing `/admin/portal-rollout` page is already the established, purpose-built home for every other portal-adoption signal this session added, so a scoped card there is the consistent choice. A dedicated idempotency-key wrapper scoped only to portal-invite sends (bypassing the shared `lib/resend.ts`/`bestEffortSms.ts` layer entirely) — rejected: it would create two different reliability models for outbound email/SMS in the same codebase, more confusing than the small residual risk it closes.

**Benefits**: `summarizeRepeatedFailures()` is pure and independently unit-tested, including a case that specifically catches an ordering bug found during its own review (naive last-write-wins over array order silently picks the *oldest* error as "most recent" when the caller's query is newest-first, since the oldest run sits last in that array — fixed to compare `occurredAt` explicitly instead of relying on iteration order).

**Drawbacks**: The ambiguous-provider-response double-send risk remains, at the same (already-accepted-elsewhere-in-the-app) level as every other outbound notification in this codebase. Revisit if it ever needs closing app-wide, not as a portal-invite-specific patch. "Recent Delivery Issues" only looks back 30 cron runs (`RECENT_RUN_LOOKBACK` in `lib/portal/deliveryIssues.ts`) — a failure pattern older than that silently ages out of view, an intentional bound against unbounded audit-log growth, adjustable if it ever proves too short.

## 41. Promotion Campaign system is a new, separate model pair — not an extension of the existing invoice-line `Promotion`

**Decision**: New `PromotionCampaign`/`PromotionCode` models (`prisma/schema.prisma`) generalize the previously-hardcoded FIRST10 offer into an admin-configurable acquisition-campaign system — percentage or fixed-dollar discount, draft/scheduled/active/retired/archived lifecycle, one designated default first-order campaign at a time, per-campaign eligibility (product allow/deny lists, min purchase, max uses, uses-per-customer), and a `PromotionStackingPolicy` (`NOT_STACKABLE` default / `STACKABLE_WITH_ONE` / `PRIVILEGED_STACKABLE` for a future Family & Friends-class campaign). This is deliberately a new model pair, not new fields bolted onto the existing `Promotion` model (`prisma/schema.prisma:873`, the flat percentage/fixed discount catalog an admin manually applies to one invoice line via `lib/promotions.ts`/`InvoiceDiscount`). `lib/promotions/campaigns.ts` is the CRUD + lifecycle service; `lib/promotions/compatibility.ts`'s `canCampaignsCombine`/`canApplyCampaignSet` is the one authoritative pairwise/set compatibility check every future consuming surface (cart, checkout, invoice, Customer Portal, admin manual invoicing) must call rather than re-deriving stacking rules independently. Admin UI at `/admin/promotions`, API at `/api/admin/promotion-campaigns[/{id}]`, and a daily `app/api/cron/promotion-campaign-schedule` route activates any `SCHEDULED` campaign whose `startsAt` has arrived without requiring an admin to be logged in at that moment (`vercel.json`, `0 16 * * *` — matching every other cron in this project, since this Vercel project is on the Hobby plan, which rejects the entire deployment outright if any cron is scheduled more frequently than daily; caught by a failed preview deployment before merge, not assumed).

This is an additive-only foundation slice: `FirstOrderOfferConfig`/`FirstOrderOfferClaim` (`prisma/schema.prisma:1899`) are completely untouched in behavior — `FirstOrderOfferClaim` gained one new nullable `campaignId` column for a later slice to populate, but `claimFirstOrderOffer()` still reads `FirstOrderOfferConfig` exactly as before. No code-issuance, discount email, or SMS wiring happens here.

**Reason**: Explicit owner instruction, confirmed after an audit found `Promotion` (despite superficially sharing the word "promotion" and the percentage/fixed discount shape) serves a structurally different purpose — an ad-hoc, admin-picked, invoice-line discount with no dates, eligibility, scheduling, or per-customer code issuance — versus a marketing acquisition campaign with its own lifecycle and audience rules. Reusing the same word for two different concepts, or bolting campaign-specific fields (start/end dates, eligible-customer-type, code-generation strategy) onto the invoice-discount picker, would make every admin creating a simple line-item discount wade through irrelevant fields, and risks the two concepts drifting into an ambiguous hybrid neither workflow is well-suited for.

**Alternatives considered**: Extending `Promotion` with campaign fields (dates, eligibility, stacking policy, a `codes` relation) — rejected per the reasoning above; audited and confirmed `Promotion`'s only real consumer today is `app/admin/settings/invoices/page.tsx`'s "Apply Promotion..." picker, a genuinely different UI/workflow that shouldn't inherit acquisition-campaign complexity. A single boolean `Promotion.stackable` generalized from the campaign spec's richer `PromotionStackingPolicy` — rejected: the spec explicitly distinguishes "not stackable" from "stackable with one" from a privileged Family & Friends class that can't stack with a second instance of itself, which a plain boolean can't express, and getting this precisely right now avoids a schema migration later once real stacking logic is consuming it.

**Benefits**: Verified against the real database — the additive schema push required no `--accept-data-loss` override once the one field that would have needed it (`FirstOrderOfferClaim.promotionCodeId`, a unique nullable FK) was deferred to the later slice that actually populates it, since an unused-today unique constraint isn't worth the risk classifier friction. ## 51. Smart manual-invoice price correction — Use Once vs Update Product Price (Phase 3B item 3)

**Decision**: `components/invoices/InvoiceItemsTable.tsx`'s Unit Price input — audited and confirmed to have zero override semantics despite `InvoiceItem.manualPricingOverride`/`priceTier: 'MANUAL'` already existing on the schema and flowing untouched through create/update (`lib/invoice/validation.ts`, `lib/invoices.ts`) — now checks, on blur (not every keystroke, so typing isn't interrupted), whether the typed price deviates from the product's catalog price for the line's selected sell-unit tier, via a new pure `checkPriceDeviation()` (`lib/pricing/lineOverride.ts`). A deviation with a real tier selected pops a small modal: **Use Once** sets `manualPricingOverride: true`/`priceTier: 'MANUAL'` on that line only, catalog untouched; **Update Product Price** PATCHes `/api/admin/inventory/[id]/pricing` with only the one changed tier field and `source: 'INVOICE_LINE_UPDATE_PRODUCT_PRICE'` (the source Decision #48 added specifically for this and left unwired until now), then sets the line's `priceTier` to the normal (non-manual) tier for that sell unit; a third **Cancel** option reverts the line to the catalog price rather than leaving a silently-unflagged deviation sitting in it. A legacy line with no sell-unit tier selected (the flat `product.price` datalist path, with no clear catalog field to attribute a change to) never triggers the prompt — editing it stays a plain line-only change, exactly as it always has been. `InvoiceBuilder.tsx` lifted `products` into local state (mirroring the existing `promotions` local-copy precedent, same file) so a successful "Update Product Price" is reflected in every other line on the same in-progress draft immediately, without a page reload that would discard any other unsaved edits on the form.

**Reason**: Explicitly requested as Phase 3B item 3, and confirmed as a real gap by the same audit that scoped items 1 and 2 — the schema and validation layer already supported a manual-override concept end to end, but no UI had ever set it, and there was no way to distinguish "typo, fix this one invoice" from "the catalog price is actually wrong, fix it going forward" — every price edit silently behaved as the former with no record of the distinction.

**Alternatives considered**: Checking the deviation on every keystroke (`onChange`) instead of `onBlur` — rejected as disruptive, since a modal popping mid-typing (e.g., after the first digit of a two-digit price) would make normal price entry unusable. Resending all four `active*` price fields from local component state on "Update Product Price" (matching the existing admin pricing page's `savePricing()` pattern, which does send all four) — rejected specifically for this call site: the admin pricing page's local state is freshly initialized from the same `product` prop it's editing, so resending all four is safe there, but an invoice line only ever has full visibility into the one tier it's using, and blindly resending the other three from a possibly-stale in-memory `products` array risked silently reverting a tier changed by someone else in the meantime — sending only the one changed field is both simpler and strictly safer here.

**Benefits**: `checkPriceDeviation()` and its two mapping helpers (`getPriceTierField`, `getInvoiceLinePriceTier`) are pure and unit-tested (13 new tests in `lib/pricing/lineOverride.test.ts`): no prompt with no tier selected, no prompt when the typed price matches exactly, a real deviation is detected and reports the correct tier field, changing Individual Vial never reads or reports Standard/SPA/Bulk (the "never accidentally modify other tiers" requirement verified directly), no prompt when the catalog has no price stored for that tier yet, and both sell-unit-to-field mappings are exhaustively checked via `it.each`. Full suite: 657/657 passing. `next build` clean. The "Update Product Price" path reuses Decision #48's audit trail with zero new plumbing — every catalog price change made this way is automatically recorded with `source: 'INVOICE_LINE_UPDATE_PRODUCT_PRICE'`, distinguishable from an admin-pricing-page edit in the same `ProductPriceChange` history table.

**Drawbacks**: The React wiring itself (blur handler, modal, the two async button handlers) has no automated test coverage — this codebase has no component-testing setup (`@testing-library/react` or similar) for any existing component either, so this follows the established convention of pure-logic unit tests plus manual/live verification rather than introducing a new test infrastructure dependency for one feature. The modal currently offers no dedicated "reason" text field for the audit trail (relies on the existing `source` distinction alone) — acceptable for this slice per the original spec's "reason where appropriate," but a future refinement could add one if `INVOICE_LINE_UPDATE_PRODUCT_PRICE` entries ever need more granularity than the source alone provides.

**Live verification**: exercised directly in production via the authenticated admin session (a preview-deployment URL redirected to a separate, unrelated Clerk sign-in instance with autofilled credentials — correctly abandoned without touching the password field, rather than authenticating there; production shares the already-authenticated session instead). Confirmed all three real product states with real catalog data: (1) selecting Semaglutide 5mg's `INDIVIDUAL_VIAL` tier surfaced the "(not on storefront)" label live, confirming Decision #50's admin bypass is genuinely working end-to-end in production, not just in tests; (2) editing its price and blurring correctly showed the exact modal text with the real catalog/typed prices; (3) **Use Once** correctly left the catalog untouched and showed the "Manual override" note; (4) **Update Product Price** on BAC Water 3ml's Standard Case ($64→$65) correctly PATCHed the real catalog (confirmed by the dropdown label updating to the new price with no error) — then reverted back to $64 via the same admin pricing API immediately after verification, so no incorrect price was left live; (5) **Cancel** on a third line correctly reverted the field to the catalog price. The test invoice itself was never saved/submitted, so no draft invoice row was left behind.

## 54. Sell-unit-aware storefront cart architecture — the foundational prerequisite for Phase 3C reorder, and a real inventory-reservation bug found and fixed along the way

**Decision**: Before Buy Again/Reorder can exist, the storefront cart needed to be able to represent more than "one flat Standard-Case-priced line per product" — audited first (Explore-agent research, not assumed) and confirmed `CartItem`/`OrderItem` had zero sell-unit concept anywhere: `lib/cart-store.ts` deduped purely on `productId`, checkout (`app/api/checkout/route.ts`) always re-priced via `getStorefrontPrice()`'s Standard-Case-only path, and `OrderItem` had no `sellUnit`/`unitsPerSellUnit` columns at all. This PR adds the foundational plumbing, with the actual Buy Again UI to follow in a later slice:
- `OrderItem` gains `sellUnit InvoiceItemSellUnit?` / `unitsPerSellUnit Int?` (additive, nullable — every existing row reads as "Standard Case" implicitly, exactly matching what checkout has always actually sold).
- `CartItem`/`CheckoutLineItem` gain the same two fields; the cart store's add/remove/update operations now key on `(productId, sellUnit)` together (`sameLine()`), so a Standard Case and an Individual Vial of the same product correctly become two separate lines instead of colliding into one.
- New `lib/storefront/checkoutPricing.ts`: `resolveCheckoutLine(product, sellUnit)` re-resolves the authoritative current price/unit-count server-side via `getAvailableSellUnits()` in its default customer-facing mode (never `adminContext: true` — Individual Vial stays gated by `individualSalesEnabled` exactly as the storefront has always enforced it), falling back to `CASE_STANDARD` when a line has no `sellUnit` (every pre-existing cart).
- `ProductDetail.tsx`'s existing "Add to Cart" button now explicitly tags its line `sellUnit: 'CASE_STANDARD'` — behavior is byte-identical to before, just now correctly labeled instead of implicit.

**A real, pre-existing bug found and fixed in the same change**: `app/api/checkout/route.ts` reserved `orderItem.quantity` physical vials directly at `reserveForOrderItemTx()` — meaning a cart "quantity" of 2 Standard Cases (10 vials each) only ever reserved 2 vials, not 20, silently understating real reservation by up to 10x for any case-tier purchase. This was a latent bug since the storefront `OrderReservation` system was first built (Decision #29) — never triggered in production because `STOREFRONT_CHECKOUT_ENABLED` has been off this entire project. New `computeVialsToReserve(quantity, unitsPerSellUnit)` fixes it: `orderItem.quantity * orderItem.unitsPerSellUnit`, now that `unitsPerSellUnit` is a real, resolved value on every line.

**Reason**: Explicitly requested as the first, foundational Phase 3C task ("build the required sell-unit-aware cart architecture first"). The reservation bug was discovered while adding `unitsPerSellUnit` — following the standing "investigate and fix a genuine bug found during approved-scope work" instruction, not a separate unplanned refactor.

**Alternatives considered**: A parallel `OrderItemSellUnit` enum, mirroring `InvoiceItemSellUnit` — rejected in favor of reusing the existing enum directly, since it's the exact same four-tier concept and Prisma enums can be shared across models with zero downside. Storing `unitsPerSellUnit` client-side and trusting it at checkout — rejected per this route's own pre-existing "never trust client-side prices" discipline; the server always re-resolves both price and unit count from the live product, the client-sent values are display-only snapshots.

**Benefits**: 8 new unit tests for the pure resolver (`lib/storefront/checkoutPricing.test.ts`): defaults to Standard Case with no sellUnit, resolves the real current price for a requested tier, resolves Individual Vial correctly when genuinely enabled, **rejects Individual Vial when `individualSalesEnabled` is false** (proving checkout never bypasses the storefront's own visibility gate, unlike the admin-context bypass from Decision #50), rejects a tier with no active price. Full suite: 668/668 passing. `next build` clean. The reservation bug fix was additionally verified against real Postgres via a disposable rehearsal script: a real product (5 vials/case, 50 in stock), a real 2-case order, confirmed `reservedUnits` actually becomes 10 (not 2) after reservation — then cleaned up.

**Drawbacks**: This slice is infrastructure only — no Buy Again button, no reorder resolver, no Customer Portal UI yet (the next Phase 3C slice). The Stripe line-item description now includes the sell-unit label (e.g. "— Individual Vial"), a small but real behavior change to what a real customer would see on Stripe's own checkout page once live — disclosed here since it's a genuine (if currently unreachable) change, not silently bundled into "infrastructure only."

## 55. Customer Portal Buy Again / Reorder UI (Phase 3C item 2)

**Decision**: New `lib/storefront/reorder.ts`'s `resolveReorderLine(request, product)` resolves one historical `OrderItem` (`productId`/`sellUnit`/`quantity`) against the CURRENT `Product` row — never a historical price snapshot. Returns either `RESOLVED` (real current `unitPrice`/`unitsPerSellUnit`, plus a `backordered` flag when the product is out of stock but genuinely backorderable — allowed through, matching how a fresh purchase already treats a backorderable item, not blocked) or `UNAVAILABLE` with one of four reasons: `product_not_found` (catalog row deleted), `discontinued` (`pricingStatus !== 'ACTIVE'`), `out_of_stock` (out of stock and not backorderable), or `sell_unit_no_longer_offered` (e.g. a historical Individual Vial purchase where `individualSalesEnabled` has since been turned off). Like Decision #54's `resolveCheckoutLine`, this always calls `getAvailableSellUnits()` in its default customer-facing mode — never `adminContext: true` — so a historical admin-composed Individual Vial line can still resolve to `UNAVAILABLE` for a customer, exactly as it should.

`app/account/orders/[id]/page.tsx` (a server component) fetches the current `Product` rows for an order's items in one query, calls `resolveReorderLine()` per line, and passes the resolved results to a new client component (`components/account/ReorderControls.tsx`): `BuyAgainButton` renders inline next to each line item — either a working button (`RESOLVED`) or a plain reason string (`UNAVAILABLE`) — and `ReorderAllButton` sits above the item list, adding every `RESOLVED` line in one click and silently skipping `UNAVAILABLE` ones (which are already individually explained inline, so no duplicate messaging in the bulk action). Both call the existing `useCartStore().addItem()` and `openCart()` — mirroring `ProductDetail.tsx`'s exact `addItem(...); toast.success(...); openCart()` pattern — and never touch checkout or payment directly; a customer still goes through Cart → Review → Checkout and authorizes the purchase themselves.

`lib/cart-store.ts`'s `addItem()` gained an optional `quantity` field (`Omit<CartItem, 'quantity'> & { quantity?: number }`), meaning "how many to add," defaulted to `1` — every pre-existing call site (`ProductDetail.tsx`'s "Add to Cart") omits it and is completely unaffected. This is what lets Reorder All add a historical quantity (e.g. 3 cases) in one `addItem()` call instead of calling it in a loop N times.

**Reason**: Explicitly requested as Phase 3C item 2, building directly on Decision #54's sell-unit-aware cart foundation. The core requirement — "historical purchases make repeat ordering easy, but all new purchases must use CURRENT product/price/sell-unit eligibility/inventory/backorder/customer pricing eligibility" and "Buy Again must not itself initiate payment" — is satisfied structurally: every price/eligibility fact comes from `resolveReorderLine()`'s live product lookup, and the only two actions available (`BuyAgainButton`/`ReorderAllButton`) are both scoped to `addItem()`/`openCart()`, with no code path in either component that can reach checkout.

**Alternatives considered**: A dedicated `/api/reorder` route that both resolves and adds server-side — rejected in favor of resolving server-side (in the page component, no new route needed) and adding client-side (the existing `useCartStore`), matching this codebase's established server-component-first convention (the same pattern `getPortalOrderDetail`/`getPortalInvoiceDetail` already use) and avoiding a redundant API surface for what's fundamentally a read-then-client-side-cart-mutation. Looping `addItem()` once per unit to add a quantity — rejected in favor of extending `addItem()` with an optional quantity parameter, since a loop would fire N separate state updates/re-renders for one user action. Silently dropping `UNAVAILABLE` lines from the list entirely — rejected per the original requirement's own framing that reasons should be surfaced, not hidden; every line always renders something.

**Benefits**: 9 new unit tests for `resolveReorderLine` (`lib/storefront/reorder.test.ts`): resolves to the CURRENT price (not a historical one), defaults to `CASE_STANDARD` for a pre-3C `OrderItem` with no `sellUnit`, all four `UNAVAILABLE` reasons individually verified, backorderable resolves as `RESOLVED` with `backordered: true` (not blocked), Individual Vial resolves correctly when genuinely still offered, and an unavailable line always reports the exact `productId` requested (never silently substitutes a different product). Full suite: 677/677 passing (up from 668). `npx tsc --noEmit`/`eslint`/`next build` all clean.

**Drawbacks**: No live browser verification of the Buy Again button itself — this environment's only authenticated browser session is the admin session, and the Customer Portal's own order pages require a real customer-side Clerk session this environment doesn't have. Verified via unit tests, typecheck, lint, and a clean production build only; a live customer-side walkthrough remains part of the existing Customer Portal QA checkpoint already tracked in `docs/PendingOwnerActions.md`. The order list page (`app/account/orders/page.tsx`) does not get its own Reorder-All entry point in this slice — only the order detail page does, since it's the page with full line-item visibility; adding a list-page shortcut is a possible future refinement, not a gap in the core requirement.

## 56. Admin-assisted reorder — Previously Purchased → Add to New Invoice (Phase 3C item 3, closing Phase 3C)

**Decision**: New `lib/admin/purchaseHistory.ts`'s `getCustomerPurchaseHistory(customerId, userId)` aggregates a customer's real purchase history from two sources — `InvoiceItem` rows linked via `Invoice.customerId`, and, when the customer has a linked storefront `User` (`customer.userId`), `OrderItem` rows linked via `Order.userId` — into one deduplicated list keyed by `(productId, sellUnit)`, keeping only the most recent occurrence of each. Historical `InvoiceItem` rows with no `productId` (the vast majority of pre-catalog-picker invoices — a real, pre-existing data gap, not something this change could retroactively fix) are excluded rather than surfaced as broken reorder links.

Each purchase-history line is resolved against the CURRENT product via `resolveReorderLine(request, product, { adminContext: true })` — `resolveReorderLine` (Decision #55) gained an optional third parameter, `{ adminContext?: boolean }`, defaulted to `false`/unset so Buy Again/Reorder All's existing calls (which pass no options) are completely unaffected. When `true`, it bypasses `individualSalesEnabled` exactly the way the admin invoice builder already does (Decision #50) — an admin can reorder an Individual Vial for a customer even when it isn't publicly visible on the storefront, mirroring what composing a fresh invoice line already allows.

A new "Previously Purchased" section (`components/admin/PreviouslyPurchasedSection.tsx`) on the admin customer profile page lists every resolved line: `RESOLVED` lines get an "Add to New Invoice" link, `UNAVAILABLE` ones show the same `REORDER_UNAVAILABLE_MESSAGE` reason text the customer-facing UI uses (now exported from `lib/storefront/reorder.ts` so both surfaces stay in sync automatically). An "Add All to New Invoice" link appears above the list when at least one line is resolvable. Both link types pass the target line(s) as a JSON-encoded `?reorderItems=` query param to `/admin/invoices/new` — chosen over a POST-based "start draft" endpoint because it's a plain navigation, matching every other link on this page, and needs no new API route.

`/admin/invoices/new` never trusts that query param's price or availability: it re-fetches the referenced `Product` rows (deliberately unfiltered by `inStock`, unlike the page's normal product-picker catalog, since a backorderable-but-out-of-stock product must still resolve) and calls `resolveReorderLine(..., { adminContext: true })` again, fresh, before seeding `InvoiceBuilder`'s draft. ## 62. Promotion code redemption at checkout — two-phase soft-hold design (Phase 4A Critical #1, PR #171)

**Decision**: Built server-side-authoritative promotion code validation and redemption for storefront checkout (`lib/promotions/redemption.ts`). Redemption is two-phase: `resolvePromotionCode()` is a pure, repeatable validation (customer eligibility including a real first-order check against both `Invoice` and `Order` history, campaign status/dates, min purchase, product eligibility, stacking, usage limits) called at both cart-preview time and checkout-creation time; `Order.appliedPromotionCodeId` is set at checkout creation as a soft hold, without ever touching `PromotionCode.status` — so an abandoned or failed checkout never permanently burns a one-time code. `finalizeRedemption()` is the *only* place a code ever becomes `REDEEMED`, called exclusively from `markOrderPaid()` on genuine payment success, implemented as a conditional `updateMany` (`WHERE status = 'ACTIVE'`) for idempotency against a redelivered webhook. Stripe's embedded Checkout line items are proportionally scaled (last item absorbs rounding) so the charged total is cents-exact with the discounted `Order.total`, rather than integrating Stripe's separate Coupon/PromotionCode object system.

**Reason**: The audit's most detailed Critical finding — explicit requirements against trusting frontend-calculated discounts, against permanently consuming a one-time code on a merely-opened (not completed) checkout, and for idempotent finalization tied to authoritative payment state.

**Alternatives considered**: A join table (`OrderPromotion`) supporting true simultaneous multi-code stacking — rejected for this slice; `Order.appliedPromotionCodeId` as a single nullable unique FK covers the stated default case (one promotion per order), and `resolvePromotionCode()` already accepts an `existingAppliedCampaigns` param so real 2-code stacking (Family & Friends + one more) can be added later without a redesign — explicitly logged as a deferred follow-up, not silently dropped. Syncing codes into Stripe's own Coupon API — rejected as unnecessary integration surface for a first working slice; proportional line-item scaling achieves the same cents-exact result with no new Stripe object type to keep in sync.

**Benefits**: Verified against real Postgres: apply → soft hold (code stays `ACTIVE`) → simulated payment success → `finalizeRedemption()` → `REDEEMED` → a second resolve correctly returns `ALREADY_USED` → a second `finalizeRedemption()` call is a harmless no-op; a separate abandoned-checkout scenario leaves the code `ACTIVE` and still usable. 7 new unit tests for `normalizePromotionCode`/`computeDiscountAmount`. Full suite 698/698, `tsc`/`eslint`/`next build` clean.

**Drawbacks**: True simultaneous 2-code stacking is not yet buildable end-to-end (the compatibility-check logic in `lib/promotions/compatibility.ts` exists and is tested, but nothing currently exercises applying 2 codes at once) — a known, intentional scope boundary, not a bug. The admin order detail page does not yet surface the applied code/discount amount in its UI (the data exists; the display doesn't yet) — a small follow-up, not a blocker.

## 69. Phase 4G: cap concurrent unpaid checkouts per email (PR #184)

The task's explicit desired behavior — "safe merge OR explicitly blocked merge with actionable admin resolution. Never: silent dead end." — is exactly what `MergeCustomersResult`'s two-variant type (`MERGED` | `BLOCKED`) enforces at the type level, not just by convention.

**Alternatives considered**: Auto-resolving ambiguous conflicts (e.g., picking whichever record has more recent activity) — rejected; the task was explicit not to guess through ambiguous identity conflicts, and a wrong auto-resolution on a `@unique` Stripe customer or portal login is a real-money/real-login-access mistake, not a cosmetic one. Soft-deleting the loser instead of hard-deleting — `Customer` has no `deletedAt`/soft-delete field anywhere in the schema, and adding one purely for this feature would be new surface unrelated to the actual gap; the loser's identity is preserved instead in the `CustomerActivityLog`/`AdminAuditLog` snapshot written immediately before deletion, and historical financial/communication records were already independently confirmed to snapshot `customerName`/`customerEmail` at creation time, so no history is lost.

**Benefits**: Verified end to end against real Postgres via a disposable rehearsal script (deleted after use): Scenario A (safe merge) — loser's `Invoice`/`CustomerAccountCredit`/`LeadCapture` correctly reassigned, the invoice's historical `customerName` snapshot untouched, loser row gone, both audit-trail entries present. Scenario B (blocked merge) — two `Customer` rows each linked to a different real `User`, zero data touched on either side, correct `BOTH_HAVE_LINKED_PORTAL_ACCOUNTS` reason returned. 10 new unit tests for `detectMergeConflicts` (every conflict type individually, one-sided-only non-conflicts, all three at once, message-quality assertion) plus the full 717/717 suite passing. `tsc`/`eslint` clean.

**Drawbacks**: `npm run build`'s `/sitemap.xml` prerender step hit this session's known local-only Neon connectivity flake (compile and typecheck both succeeded first) — relied on Vercel's CI build, which has stable database access, as the authoritative check, consistent with the Phase 4H/4N precedent for the same class of local-only issue.
